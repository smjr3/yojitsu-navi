# プロジェクト引き継ぎ資料（開発コンテキストの移行用）

クラウドの開発環境（プロジェクトの会話・プロジェクトメモリ）に溜まった情報を、ローカルの開発環境へ移すためにまとめた資料。作成時点は main が PR #80 までマージされた状態。

> **この資料の書き方について**
> - リポジトリの決まり（[CONTRIBUTING.md](../CONTRIBUTING.md)「アカウント名を書かない」、npm パッケージの検査）に合わせて、個人名・アカウント名・会社名・社内 URL・メールアドレスは書いていない。発注者・利用者は「依頼者」と書く。
> - 試用版・設計案・QA 一覧などの外部ページの URL も、アカウントに結びつくため書いていない（場所は依頼者が知っている）。
> - 推測で補っていない。元の情報を確認できなかったものは「7. 取得できなかった・未確認の情報」に書いた。
> - 日付はプロジェクトの会話・メモリにある日付をそのまま書いた（年は 2026 年、年度は 4 月始まり）。
> - この資料は `docs/` にあるため、アプリの npm パッケージ（`yojitsu-navi`）のひな形にも入る。

## 1. プロジェクトメモリに保存されている情報

プロジェクトメモリは、1 つの索引ファイルと、テーマごとのメモ約 30 件でできている。中身を種類別にまとめる（細かい仕様は [SPEC.md](SPEC.md) が正）。

### 1.1 依頼者について・進め方の好み

- 依頼者は音声入力を使う。誤変換は文脈で補う（例:「仕様版」は「試用版」）。
- 返事は結論から短く書く。感想はいらない。
- 指示は試用版（公開した動くデモ）へのコメントで来ることが多い。
- 依頼者はターミナルを使わない。GitHub の操作は画面での手順で案内する。

### 1.2 厳守ルール（依頼者の指示）

| ルール | 内容 |
|---|---|
| 指摘は横展開する | 1 か所への指摘は、同じ部品・考え方を使う他の箇所にも当てはめる。過去に漏れていた箇所は「これも必要では」と提案する |
| 個人・会社情報を書かない | リポジトリにも npm パッケージにも、アカウント名・社内 GitLab の URL などを書かない。接続先は本番側の設定で渡す |
| 年度・年月を固定で書かない | SPEC §49。`no-fixed-year` テストで検査（対象はソース・スクリプト・設定。docs は対象外） |
| 「今日」は閲覧者の日本時間の日付 | 取り込み日時は「いつ時点のデータか」として別に表示する。環境変数 `YOJITSU_AS_OF` はテスト・デモ用だけ |
| 画像をリポジトリに置かない | README のスクリーンショットも禁止（PR #69 で全部削除）。テストと npm pack の検査で再混入を防ぐ |
| docs は同じ PR で直す | 古い説明を残さない |
| Windows・Linux の両方で動かす | 本番の GitLab Runner は Windows（Linux に変わる可能性あり）。CI の script は Node のスクリプトと `npm run` だけ、改行は LF 固定、パス・言語設定に依存しない（SPEC §79） |
| 画面に説明文を増やさない | 説明は見出し横の「?」だけ。GitLab の設定は設定画面（/settings）1 か所だけ |
| テストは手厚く | ユニット・E2E に加え、実際の操作で QA（幅 390/768/1024/1280、ライト/ダーク、極端な値）。UX も評価してから報告 |
| PR レビュー | Codex の PR レビューが有効。コメントに対応してからマージ |
| ブランチ | マージ済みブランチは削除（GitHub の自動削除が有効）。既定ブランチは main |

### 1.3 用語（言い換え済みのもの）

| 旧 | 現在 |
|---|---|
| 売上 | 予算 |
| 原価 | 実績 |
| 粗利 | 残予算 |
| 赤字 | 超過見込み |
| 契約 | 案件 |
| 稼働計画 | リソース計画（/plan） |
| 契約外 | 運用保守以外 |
| メンバーID | 社員番号 |

- 所属は事業本部・部・課の 3 段。
- 「不在」は 2 値だけ（在籍／不在）。CSV の欄が空なら在籍、何か書いてあれば不在。理由は画面に出さない。取り込みで自動的に在籍に戻さない。選択肢を増やす提案はしない。
- 応援＝管理対象内の他チームの人が案件に稼働する（計画あり）。ヘルプ＝他部署の人がスポットで稼働する（実績だけ。マスタに登録すれば役職単価で計算し、未登録なら 0 円）。どちらも運用保守の実績に含め、見分けられるようにする。
- 作業種類は、人ごとに実際にあるものだけを出す（表示期間内に計画か実績がある種類）。追加は「＋ 作業」から検索して選ぶ（年間 100 種類を超える人がいる）。

### 1.4 仕様の要点（メモリの要約。詳細は SPEC）

- **計算**: 予算＝契約総額の均等月割り。実績＝工数×時間単価。年度は 4 月開始。工数は翌月 3 営業日で確定。金額は税抜。100% を超えたときだけ赤。金額の既定単位は百万円（切り替え可）。
- **着地見込み**: 計画値（既定）／直近 3 か月／全実績から選べる（§54）。期間プリセット「今後 3 か月」（§34）。
- **画面の骨組み**: 上部タブと固定フィルタ。右上は「リソース計画」ボタンだけ（選択中のチームを引き継ぐ、#76）。マスタ編集・使い方・データ確認・計算ルールは「⋯」メニュー。
- **マスタ編集**（§24〜29）: GitLab のマージ方式。保存するとブランチと MR を作り、Maintainer だけがマージできる。mode "demo" ではブラウザ内の模擬 GitLab を使う。本番構成は [DEPLOY_GITLAB.md](DEPLOY_GITLAB.md)（§39）。
- **設定画面**: トークン欄に「トークンを作成 ↗」ボタン（#80、§78）。開く先は config.json の tokenUrl、空なら GitLab 標準のパス。接続先プロジェクト名も GitLab へのリンク。デモでは無効表示。最下部にバージョン表示（§59）。
- **リソース計画**: 対象ごとに 1 行と変更履歴（§36）。人月か時間で入力。月別の積み上げ棒グラフ。変更者・変更日を自動記録（§56）。「変更の影響」プレビュー（§65）。期間は「◀ 開始月〜終了月 ▶」で自由に指定、初期は今月から 12 か月（#70、§71）。内訳行は青帯（#68）。配分は 0 以上なら保存でき、1.0 を超えると警告だけ出す（#79）。検証の文言は日本語。
- **運用保守以外の稼働**も管理する（§50）。作業名のキーワード（含む／除く、`|` 区切り）で運用保守を抜き出す（#50、§62）。作業種類は data/task-types.csv の group 列から決める（デモ値は仮）。
- **配色**: 表示モード（自動／ライト／ダーク）。テーマカラーは GitLab の theme_id に連動（src/components/appearance.js）。フォントは BIZ UDPゴシックを同梱（§46）。
- **文言**: src/i18n/ja.js・rules.txt・guide.txt。使い方はアプリの中にある（§47）。
- **npm**: パッケージは `yojitsu-navi` 1 つ（アプリ一式を作るコマンド＋ import できる計算コア。§44・§84）。npmjs.com に公開（MIT、§83）。
- **更新でローカルの変更を守る**（§86）: `yojitsu-navi update` は `config.json`・`data/` を残し、ほかを上書きする。社内で変えたファイルがあれば上書き前に止まる（`--dry-run` で差分、`--overwrite`／`--keep-local` で選ぶ）。前のファイルは `.yojitsu-navi-backup/<日時>/`。利用者に届けるには版を上げて公開が要る。
- **案件の一覧・祝日**（§80）: マスタ編集の「案件」タブ（data/contracts.csv。顧客・案件名・開始月・終了月・金額・担当チーム）と「祝日」タブ（data/holidays.csv）。保存は GitLab のマージ。**案件の顧客名・案件名は他システムから API で取り込む予定なので、直せるのは期間・金額・担当チームだけ**（行の追加・削除・CSV 編集なし）。金額・期間・祝日の変更で過去の月が変わるときは確認を出す。作業種別は作業名から抜き出す運用になるのでタブにしない（依頼者 2026-11-01）。
- **メンバーの社員番号・氏名は画面で変えない**（§81）: 人事から取り込むため、保存済みの行では読み取り専用。メンバーの CSV 編集もなし。**所属は取り込まず画面で直す**（依頼者 2026-11-01。既定の config.json の memberSource.columns から所属を外した）。
- **目標値**（§63、data/targets.csv）: 残予算率だけ、月単位、マイナス可。目標がある対象では、進捗の上限・推移線とも目標を優先。変更者・変更日を記録（#76）。
- **今月の進捗**（§61）: 日別の速報。月次推移を上に置く。凡例は 累計＝実線、月末見込み＝点線、目安・上限＝破線。「今日」の縦点線（#75）。計画と実績のずれ一覧（#54、§64）。変更の影響プレビュー（#53、§65）。
- **見た目の決まり**（§66〜69）: フィルタバーは幅 1280px 以上で 1 行（#57、#76 で他の画面にも展開）。超過の赤は合計の着地がマイナスのときだけ。上段の高さ 32px。
- 案件詳細の明細は氏名で表示し、列名は「配分（人月）」（#59）。離任月に計画か実績があれば稼働扱い（#58）。
- **役職**はプルダウン（#73、§31.5）。候補は単価マスタの役職と既存の役職。役職マスタは作らない。事業本部／部／課も既存値を候補に出し、新規入力も可。組織マスタは作らない（#76）。
- **列ごとの絞り込み**（#61、§70）: 表の共通部品（dataTable）に漏斗ボタン。合計は絞り込み後に計算し直す。木構造の表とマスタ編集の表も対応（#76。一致した行は親も表示し、親は薄い字）。一覧表はすべて列幅をドラッグで変えられ、ダブルクリックで元に戻る（§77）。
- **体制図**（#77、§76）: 事業本部〜メンバーのツリー。月送り。着任・離任・応援による増減。色は計画稼働／ずれ・残予算率。ホバーで、チームなら担当顧客、メンバーなら実績（過去）・予測負荷（未来）。表示専用。チーム一覧の見出し右の「体制図」で切り替える。
- **顧客詳細「メンバー別の実績」**（#74、§74）: 「担当チーム別」の下に、全案件をまたいだ人別の時間・金額・構成比と応援／ヘルプ。クリックで内訳。
- **今日＝日本時間**（#75、§75）: 取得日時が前日より前なら警告色。「計算基準日」の表記は「今日」に変更。
- **試用版のデモデータ**: 固定日付をやめ、公開日（10/31）を基準に作る。取得日時は「10/31 9:00」のまま。このため 11/1 以降は今月の進捗が 11 月（実績 0）になり、11/2 以降は取得日時が警告色になる（取り込みが止まったときの見え方の確認になる）。試用版コメントで「おかしい」と来たら、この仕様を説明する。

### 1.5 メモリにある運用上の注意

- **試用版コメントの割り振り**: 見た目・小さな修正は、試用版コメントを見張るスレッド「試用版の見た目の指摘を直す」1 本が担当し、機能追加だけ別スレッドにする。同じコメントを複数のスレッドに割り振らない（#60・#63・#67 が重複でクローズになった）。着手前に open PR を確認する。
- **試用版の公開**: 公開ツールは、拡張子のないページを text/html として載せられない。公開物の中のページリンクをすべて「./xxx.html」に書き換えてから公開する。
- **CI が止まっているとき**（GitHub Actions の無料枠切れ。予算は追加しない。11-01 に復活を確認）: ローカルで全テスト（`npm run check` と全 E2E、約 60 分。`PW_CHROMIUM_PATH=/opt/pw-browsers/chromium`）が通ればマージしてよい。CI は PR でスモーク、main でだけ全 E2E（3 分割、SPEC §82）。
- **クラウド環境の制約**: 自スレッド以外のブランチ削除やリポジトリ設定の変更はできない（403）。依頼者が GitHub の画面で行う。
- **本番データ環境との差を前提にする**: 自動取得を前提にするのは作業実績と人事だけ。列名・形式の差は設定で吸収し、構造の差は改修が必要。

## 2. 目的・設計思想・開発方針

### 2.1 目的

- 社内チームの**保守案件の予実（予算と実績）とリソース計画**を見るダッシュボード。
- 閲覧者は経営層からメンバーまで。ブラウザだけで見る。閲覧の制限はしない。
- 社内 GitLab Pages で配信する（GitLab CI は使える）。他の AI・SaaS はほぼ使えない環境。
- アプリ名は現在「予実ナビ」（変更を検討中。6 章）。

### 2.2 設計思想（会話とメモリにある考え方）

- **汎用的に作る**: 特定の組織の作りに依存しない。チームは何段でも入れ子にでき、案件は個別に扱う。
- **集計は作業実績に合わせる**: チームの所属ではなく、実際の作業実績で集計する。紐付けのコードがないため、名前の対応表で結ぶ。顧客に結びつかない作業は対象外。
- **計算の根拠を画面で確かめられる**: 「計算ルール」画面と、見出し横の「?」。
- **画面に説明文を書かない**: 動的に組み立てた文章も出さない。説明は「?」とアプリ内の使い方に寄せる。
- **マスタは Git を知らなくても直せる**: 画面から編集し、裏では GitLab のブランチと MR を作る。マージはリーダー層（Maintainer）だけ。
- **本番データとの差は設定で吸収する**: 列名・日付・単位は config.json で合わせる。
- **妥協しない**: 世界水準のダッシュボードの作法を参考にし、徹底したテスト（モンキーテストを含む）で品質を保つ。

### 2.3 技術構成

- Observable Framework 1.13 の静的サイト。データは data/ の CSV。データローダーとキャッシュの扱いは [DATA_LOADERS.md](DATA_LOADERS.md)。
- 計算コアは純粋な TypeScript（src/core）。npm パッケージ `yojitsu-navi` から import できる（[CORE_NOTES.md](CORE_NOTES.md)）。
- アプリ一式も npm 化（packages/app）。ひな形は `git ls-files` から .github を除いたもの。
- テスト: Vitest（ユニット・結合）、Playwright（E2E）。
- 文書: 仕様 [SPEC.md](SPEC.md)、データ [DATA.md](DATA.md)、ダミーデータ [DUMMY_DATA.md](DUMMY_DATA.md)、運用 [OPERATIONS.md](OPERATIONS.md)、文言 [TEXTS.md](TEXTS.md)、画面のメモ [UI_NOTES.md](UI_NOTES.md)、本番 GitLab [DEPLOY_GITLAB.md](DEPLOY_GITLAB.md)、npmjs.com への公開 [RELEASE.md](RELEASE.md)。

### 2.4 開発方針（CONTRIBUTING とメモリ）

- docs は同じ PR で直す。どの領域を変えたらどの文書を直すかは [CONTRIBUTING.md](../CONTRIBUTING.md) のチェックリストに従う。
- 画像はコミットしない。
- マージ前に `npm run check` と `npm run test:e2e`（全件）をローカルで通す。
- 実際の操作で確認する（390 / 768 / 1024 / 1280px、ライト / ダーク、極端な値・長い名前）。
- 文言は src/i18n/ja.js・rules.txt・guide.txt に置く。
- ビルドは必ず `npm run build` を使う（直接 `npx observable build` を呼ばない）。
- PR はテンプレート（変更内容・ドキュメント・テスト）に沿って書く。Codex のレビューに対応してからマージする。

## 3. 過去の指示・要望・重要な意思決定

プロジェクトの会話に残っている依頼者の指示を、おおむね時系列でまとめる（言い回しは要約）。

### 3.1 要件ヒアリング（10-27）

- 保守契約の予算と実績を管理したい。汎用的な作りにする。npm 化は後で。GitLab Pages で配信。閲覧はメンバーから経営層まで。
- 配分は 1.0 人月を基本に、月ごとに変えられる。実績＝工数×役職ごとの時間単価。パートナーは個別単価。
- 予算は均等月割り。1 人月＝160h と、暦に基づく値の両方。過去の月は再計算しない。100% 超は赤。
- 集計はチームではなく作業実績に合わせる。紐付けコードがないため名前の対応表を使う。顧客に結びつかない作業は対象外。案件ごとに着地見込みを出す。閲覧制限なし。リーダーが Git のファイルで入力する。
- マスタは Git を触らずに直したい。計算の根拠を画面に出す。チームは何段でも入れ子。案件は個別。作業実績は API から取る。期間は自由に選べる。人ごとの予実も見たい。
- 品質管理を徹底する。テストは徹底的に（モンキーテストを含む）。世界水準の作法で。妥協しない。

### 3.2 画面・運用の指示

- 左ナビの案は見た目が悪い → A 案（上部タブ）に決定。動的に組み立てた文章は出さない。
