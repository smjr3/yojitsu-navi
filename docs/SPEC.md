# 予実ナビ 計算仕様（実装の正）

要件定義（2026-10-27 確定）を実装可能な粒度に落としたもの。画面・テスト・計算コアはこの仕様に従う。
型は `src/core/types.ts`。設定は `config.json`。

## 1. 用語

| 用語 | 意味 |
|---|---|
| 案件 | 予実を管理する単位。1 案件 = 1 契約（`contracts.csv` の 1 行）。契約の更新・金額変更は同じ案件の別の契約行（別 ID）として持つ（§32） |
| 予（予算） | 保守契約の総額を契約月数で均等割りした月次の予算額 |
| 実（実績） | 作業時間 × その月に有効な時間単価。種類（`costTypes`）を持つ。当面は `labor` のみ |
| 残予算 | 予算 − 実績。残予算率 = 残予算 ÷ 予算 |
| 消化率 | 経過月の累計実績 ÷ 経過月の累計予算。100%超（`burnRateDangerThreshold`）で赤 |
| 着地見込み | 選んだ期間の終わり時点の実績と残予算の予測。案件（契約）ごとに超過／範囲内（§54） |
| 年度 | 4月始まり（`fiscalYearStartMonth`）。FY2026 = 2026-04〜2027-03。年度番号は開始年 |
| asOf | 計算基準日（＝今日）。画面を開いた人の今日（日本時間）。ビルド時の値はビルドした日で、画面で置き換える（§75）。テスト・試用版は `YOJITSU_AS_OF` で固定する |
| リソース計画 | 人 × 案件 × 月の配分（アサイン）と契約外予定を入れる画面 `/plan`（§23・§36）。旧称: 稼働計画（改名は §48。URL・ファイル名・データ構造は変えない） |

画面の用語（2026-10-28 変更）: 予実管理なので「売上」「原価」「粗利」「赤字」「黒字」は使わない（予実の差のマイナス＝超過で表す）。コード上の名前はそのまま（`cost` = 実績、`grossProfit` = 残予算、`grossMargin` = 残予算率、`forecastGrossProfit` = 着地差、`deficit` = 超過見込み、`isOverBudget` = 消化率超過）。画面の文言は `src/i18n/ja.js`。

## 2. 月の扱い

- 年月は `"YYYY-MM"` の文字列。比較は文字列比較で正しい（ゼロ埋め必須）。
- 契約の月数 = 開始月と終了月を**両方含む**月数。`2026-04`〜`2027-03` は 12。
- 月途中開始・終了も均等割り（日割りしない）。
- `startMonth > endMonth` の契約は `CONTRACT_INVALID` 警告を出し、計算から除外する。
- `totalAmount < 0`、数値でない、整数でない場合も `CONTRACT_INVALID`。0 は有効（予算0）。
- 契約IDの重複は `DUPLICATE_CONTRACT_ID`。最初の行だけ採用。

## 3. 月次予算

```
baseMonthly = floor(totalAmount / monthCount)
remainder   = totalAmount - baseMonthly * monthCount
budget(m)   = baseMonthly            (最終月以外)
            = baseMonthly + remainder (最終月)
```
- 全月の合計は必ず `totalAmount` と一致する（テストで保証）。
- 内訳 `BudgetBreakdown` に `totalAmount, monthCount, baseMonthly, remainder, isLastMonth` を入れる。

## 4. 作業実績の紐付け（名称マッピング）

### 4.1 正規化
顧客名・案件名は照合前に `normalizeName()` で正規化する。
1. Unicode NFKC（全角英数・半角カナを統一）
2. 前後の空白を除去、連続する空白（全角含む）を1つの半角空白に
3. 小文字化
4. 法人格の除去: `株式会社`, `(株)`, `（株）`, `㈱`, `有限会社`, `(有)`, `（有）`, `㈲`, `合同会社`, `Inc.`, `Co., Ltd.`, `Ltd.`, `Corp.`, `LLC` を**前後から**除去（中間は残す）。除去後に再度 trim。
5. 空になったら空文字。

### 4.2 照合
1. 顧客名が空（正規化後）の工数は**除外**。`excludedHours` に合算し `EXCLUDED_NO_CUSTOMER` 警告1件（時間と件数）。
2. キー `(顧客, 案件)` の完全一致ルールを探す。無ければ `(顧客, "")` のルールを探す。
3. 該当ルールが指す契約のうち、作業日の月が `startMonth..endMonth` に含まれる契約を選ぶ。
   - 1件 → その契約に紐付け。
   - 0件 → 未紐付け（理由 `OUT_OF_PERIOD`）。
   - 2件以上 → `contractId` 昇順で最初を採用し `MAPPING_AMBIGUOUS` 警告。
4. ルールが無い → 未紐付け（理由 `NO_RULE`）。
5. ルールの `contractId` が存在しない → `MAPPING_UNKNOWN_CONTRACT` 警告、未紐付け（理由 `UNKNOWN_CONTRACT`）。
   ルールの `contractId` が不備で除外中の契約 → `MAPPING_EXCLUDED_CONTRACT` 警告（除外理由つき）、未紐付け（理由 `EXCLUDED_CONTRACT`）。
6. 未紐付けは `(顧客名, 案件名)`（元の表記）でまとめ、時間・件数・最初と最後の日付を持つ。
7. ルールに作業名のキーワード（`task_include` / `task_exclude`）があるときの振り分けは §62。作業コードの行・行の期間（`task_code` / `start_month` / `end_month`）は §92。mapping.csv に行の無い作業を作業名から抜き出した案件名で紐付けるのは §97。

`hours <= 0` または数値でない工数行は無視する（紐付け・未紐付けのどちらにも数えない。データ確認の検証に `WORKLOG_INVALID_HOURS` で件数を出す）。`hours` は小数可（0.25 など）。

判定の全体の順序・未紐付けの扱い・契約の更新のときの扱いは §86 にまとめる。

## 5. 履歴マスタの「有効レコード」

teams / members / rates は `effectiveFrom`（適用開始月）付きの履歴。
**月 m に有効なレコード = 同じキーで `effectiveFrom <= m` のうち `effectiveFrom` が最大のもの**。
同じキー・同じ `effectiveFrom` が複数ある場合は後の行（ファイル末尾側）を採用。
`effectiveFrom > m` しか無ければ「その月には存在しない」。

## 6. 時間単価

月 m のメンバー x の単価:
1. `rates` に `key == memberId` の有効レコードがあればそれ（パートナー個人単価）。
2. 無ければ、月 m に有効な `members` レコードの `title` で `key == title` を探す。
3. 無ければ単価 0、`rateMissing = true`、警告 `RATE_MISSING`（社員番号・月ごとに1件、時間を合算）。
4. メンバーが `members` に無い → 単価は 1 のルールのみ試し、無ければ 0。警告 `UNKNOWN_MEMBER`（社員番号ごとに1件）。

単価改定は行を追加する運用。過去月は過去の単価で計算されるので再計算されない。

## 7. 月次の実績

契約 c、月 m:
```
costLines = 作業ログを (memberId) でまとめ、
            hours = Σhours, hourlyRate = 単価(member, m),
            amount = round(hours × hourlyRate)   // 円に四捨五入（Math.round）
cost(c,m)  = Σ amount
costs[labor] = cost
```
- 実績の種類: 当面 `labor` のみ。`costs` は `config.costTypes` の全IDをキーに持ち、無い種類は 0。合計 `cost = Σ costs[*]`。
- `costLines` にはそのメンバーの当時のチームID（members 有効レコードの `teamId`）を持たせる。
- `worklogs` に元の作業ログ（契約IDと単価・金額付き）を持つ。
- 作業ログの `date` が不正（`YYYY-MM-DD` でない・存在しない日付）な行は無視する。

## 8. 月の状態（確定・速報・未来）

- `asOfMonth` = asOf の年月。
- 月 m の確定日 = m の翌月の第 `closingBusinessDay` 営業日（営業日 = 土日でも `holidays` でもない日）。
- `status(m)`:
  - `m > asOfMonth` → `future`
  - `m == asOfMonth` → `preliminary`
  - `m < asOfMonth` かつ asOf < 確定日 → `preliminary`
  - それ以外 → `final`
  - 契約期間外の月は `ContractMonth` を作らない（`outside` は集計時の表現用）。
- `meta.lastFinalMonth` = 状態が `final` の最大月（asOf 月の前月か前々月）。

## 9. 営業日数と人月換算

- `businessDays(m)` = m の暦日のうち土日と祝日（`holidays.csv`。行の無い年は国民の祝日で補う。§49）を除いた日数。
- 人月（標準）= hours ÷ `standardHoursPerMonth`。
- 人月（カレンダー）= hours ÷ (businessDays(m) × `hoursPerBusinessDay`)。複数月の合計は月ごとの人月を合算。

## 10. 着地見込み（案件＝契約ごと・対象の月ごと）

対象の月 `targetMonths` = 画面で選んだ期間の月（§54。`model.json` に入る既定値は asOf の年度の 12 か月）。契約 c について:

```
cMonthsInTarget = targetMonths ∩ 契約期間                // contractMonthsInTarget
actualMonths    = cMonthsInTarget のうち m < asOfMonth   // 完了した月（速報含む）
remainingMonths = cMonthsInTarget のうち m >= asOfMonth  // asOf 月を含む
targetBudget    = Σ budget(c, m)  for m in cMonthsInTarget
actualCost      = Σ cost(c, m)    for m in actualMonths
```
残り月の実績の出し方（方式）:
- `recent3`: 契約期間内で `m < asOfMonth` の月（年度をまたいでよい）のうち直近 `forecastRecentMonths` か月の実績の平均 × 残り月数。基礎月が 0 → 平均 0、`noActuals = true`。基礎月が 3 未満ならある分で平均。
- `all`: 契約開始月から `m < asOfMonth` までの全月の実績の平均 × 残り月数。基礎月 0 → `noActuals`。
- `assignment`: Σ(残り月 m, アサイン a: a.memberId, a.contractId == c, a.startMonth <= m <= a.endMonth) allocation × `standardHoursPerMonth` × 単価(a.memberId, m)。アサインが0件 → `noAssignments = true`、残り見込み 0。

```
forecastCost        = actualCost + remainingCost
forecastGrossProfit = targetBudget - forecastCost
isDeficit           = forecastGrossProfit < 0
```
契約が対象の月に1か月も掛からない場合: `targetBudget = 0, forecastCost = 0, isDeficit = false`、`contractMonthsInTarget = []`。
3方式すべてを `forecasts` に入れ、画面で切り替える。

## 11. 集計（画面側）

`aggregate(model, scope)`:
- `scope.period = {from, to}`（両端含む）。`scope.contractIds`（省略 = 全契約）。
- 期間内の `ContractMonth` を合算: budget, costs, cost, grossProfit, hours。
- `grossMargin = grossProfit / budget`（budget 0 → null）。
- 消化率: `elapsedMonths` = 期間内かつ `m <= asOfMonth` の月。`burnRate = Σcost(elapsed) / Σbudget(elapsed)`（分母 0 → null）。`isOverBudget = burnRate != null && burnRate > threshold`。
- `includesPreliminary` = 期間内に `preliminary` の月を含む。
- `monthlySeries(model, scope)` → `MonthlyPoint[]`（期間の全月。契約の無い月は 0・status は asOf 基準で計算）。
- `forecastTotals(model, contractIds, method)` → 契約ごとの着地を合算、`deficitContractIds` を列挙。

### チーム
- `teamTree` は asOf 月に有効な `teams` レコードで作る。親が存在しない `parentTeamId` は `UNKNOWN_TEAM` 警告を出し最上位扱い。循環参照は検出して切る（警告 `UNKNOWN_TEAM` に理由を書く）。
- チームの案件 = `contract.teamId` が自分または配下（`descendantIds`）に含まれる契約。上位組織の数値は配下すべての合計。
- 主担当チームが空・未知の契約は「未設定」という仮想グループに入れる（チーム一覧の末尾に表示）。
- 過去月の組織は当時のもので集計する: `teamTreeAt(model.dataset, month)` を用意し、チーム一覧は期間の終了月の組織で表示する（初回リリースはこれで十分。月ごとの組織差分は2回目以降）。

## 12. 金額・表示

- 内部は常に円の整数（実績は行ごとに四捨五入）。
- 表示は **百万円（既定、2026-10-27 決定）**／千円／円を切替。百万円は `Math.round(yen / 100000) / 10` を小数1桁で表示（例 `12.3百万円`）、千円は `Math.round(yen / 1000)`。
- 計算根拠パネルの「実際に使った値」（契約総額・単価・作業ログの金額など）は単位に関係なく円で表示する（根拠は丸めない）。
- 明細の表（作業ログ、実績行＝メンバー×月の実績、メンバー×月・メンバー×契約の計画/実績、単価）は 1 行の金額が小さく百万円では 0.0 になるため、**選択単位に関係なく円** で表示し、見出しに「（円）」と書く。選択単位に従うのは KPI・一覧（契約・チーム・顧客・メンバーの集計行）・月次推移。
- 金額に添える文（「計画より実績が少ない」等）の判定は、表示に丸めた後の値で行う（「±0.0百万円」なのに「少ない」と出さない）。
- Excel 出力の金額は単位に関係なく円の整数。
- 割合は小数1桁（例 103.4%）。
- 赤表示は消化率 > 閾値 と 着地が超過見込み のみ。黄色警告は無し。チーム・顧客・全体など案件をまとめた単位の超過見込みは、合計の着地がマイナスのときだけ赤（§67）。
- 例外: マスタ編集・リソース計画の検証は、保存を止める **エラーを赤**、止めない **警告を黄** で分ける（§40）。

## 13. 計算根拠（内訳）

すべての表示値は根拠を持つ。
- 予算: `BudgetBreakdown`
- 実績: `CostLine[]` → `WorklogEntry[]` まで辿れる
- 消化率: `burnRateBreakdown`
- 着地: `ForecastBreakdown`
画面の数値をクリックすると内訳パネルに「式 ＋ 実際に使った値」を表示する。

## 14. データ検証（CI で止める）

`scripts/validate-data.ts` は以下で非0終了する:
- 契約: ID重複、期間逆転、金額が数値でない／負／円の整数でない／9,007,199,254,740,991 円超、主担当チームが teams.csv に無い（`CONTRACT_UNKNOWN_TEAM`）
- マッピング: 存在しない契約ID
- アサイン: 未知の社員番号／契約ID、allocation が 0 未満・数値でない（1.0 超は受け付ける。2026-10-31 試用版のコメント。1 人の月合計 > 1.0 は下の警告）
- チーム: 未知の親ID、自分自身を親にした行（`TEAM_SELF_PARENT`。行番号つき）、循環、未知のリーダー（`TEAM_UNKNOWN_LEADER`。§22）、同じ team_id・effective_from の重複行（`DUPLICATE_TEAM_ROW`）
- メンバー: 未知のチームID、区分が employee/partner 以外、同じ member_id・effective_from の重複行（`DUPLICATE_MEMBER_ROW`）
- 単価: 数値でない／負、同じ key・effective_from の重複行（`DUPLICATE_RATE_ROW`）
- CSV: 引用符（"）の閉じ忘れ（`UNCLOSED_QUOTE`。開始行を示す）
- 日付・年月の形式不正
警告（未紐付け工数、単価なし）は止めずに表示する。追加の警告:
- 役職の単価が rates.csv に 1 行も無いメンバー（個人単価も無い）。役職ごとにまとめる（`MEMBER_RATE_UNDEFINED`）
- アサインが契約期間の外にはみ出している（`ASSIGNMENT_OUTSIDE_CONTRACT`。はみ出した月は計画に入らない）
- 1 人の月合計 allocation > 1.0（`ALLOCATION_OVER_1`。2026-10-29 にエラーから警告へ。同じ人の続いた月は 1 件にまとめ、期間と最大値を示す。§40）
- 1 人 1 日の作業実績が 24 時間超（`WORKLOG_DAY_OVER_24H`。先頭 5 件を例示。計算には含める）
- メンバーの effective_from より前の作業による単価なしは、原因が分かる文言にする（`RATE_MISSING`）

## 15. CSV の規約

- UTF-8（BOM あり可）。Shift_JIS も読み込み時に自動判定（`scripts/` で対応）。
- 1行目はヘッダ。列名は英語（`contract_id` など）で、`docs/DATA.md` に列定義を置く。
- 空行・空白だけの行は無視。
- 数値セルのカンマは 3 桁区切り（`1,234`）としてだけ受け付ける。`1,5` のような形は不正値（小数のつもりの入力を 10 倍に読まないため）。
- 金額の先頭の `¥`・末尾の `円` は取り除いて読む（`¥1,200,000` → 1200000）。
- 作業実績の日付は `YYYY-MM-DD` のほか `YYYY/MM/DD`・`YYYY/M/D` も受け付け、`YYYY-MM-DD` に揃える。不正な行は先頭 5 件をファイル名・行番号・値つきで警告に出す。
- 作業実績フォルダのファイル名は `YYYY-MM.csv`（拡張子の大文字小文字は問わない）。それ以外の名前の CSV（`2026-10 (1).csv` など）は読まずに `WORKLOG_FILE_SKIPPED` 警告。
- 列の欠落・引用符の閉じ忘れがあるファイルは、そのエラーだけを出し、同じ原因で起きる行ごとのエラーは出さない。

# 2回目リリースの追加仕様（2026-10-28）

範囲: チーム詳細（§16）、顧客別（§17）、メンバー別（§18）、マスタ編集（§19）、本番APIの列名対応（§20）。
画面の共通ルール（数値列の並び・赤の条件・根拠ボタン・Excel 出力・URL 状態）は初回と同じ（`docs/UI_NOTES.md`）。

## 16. チーム詳細 `/team?id=<teamId>`

問い: 「このチームはなぜ悪いか」。
- 母集団 = §11 と同じ（`contract.teamId` が自分または配下の契約。組織の基準月は `min(期間の終了月, asOf 月)`）。`id=__unassigned__` は「未設定」グループ。
- 構成: パンくず（上位チームを辿れる）→ KPI（初回の全体サマリーと同じ5枚）→ 月次推移 → 配下チーム（直下の子ごとの行。子が無ければ出さない）→ 案件一覧（チームの案件のみ）→ メンバー別実績（このチームの案件に工数を付けた人。所属チームが別でも含める＝作業実績軸）→ 組織の変遷（期間内に親・名前が変わった場合だけ、月と内容を列挙）。
- 存在しない ID・期間内に存在しないチームは空状態で「このチームは選択期間の組織にありません」とし、チーム一覧へのリンクを出す。
- チーム一覧の行・全体サマリーのチーム別の行からチーム詳細に遷移できるようにする（初回の「案件一覧に絞り込み」はチーム詳細内のリンクに移す）。

## 17. 顧客別 `/customers`、`/customer?key=<customerKey>`

問い: 「どの顧客が悪いか」「この顧客の案件はどうか」。
- 顧客キー `customerKey = normalizeName(contract.customerName)`（§4.1）。表示名はそのキーの契約のうち **契約ID昇順で最初の契約の `customerName`**。キーが空の契約は「顧客名なし」グループ（キー `__none__`）。
- 一覧: 顧客ごとに案件数（期間内）・標準数値列（予算・実績・残予算・残予算率・消化率・着地差）・状態チップ（超過見込み件数・予算超過）。チームで絞り込める（チームの案件に限定した顧客集計）。検索欄（`normalizeName` で部分一致）。
- 詳細: KPI → 月次推移 → 案件一覧（その顧客の契約）→ 担当チーム別（契約の `teamId` ごと）→ メンバー別の実績（§74）→ 作業種別の内訳。
- 前年同期比は初回と同じ規則で KPI に出す（前年データが無い間は「比較データなし」）。

## 18. メンバー別（人ごとの予実） `/members`、`/member?id=<memberId>`

要件: 人ごとの予＝配分人月×基準時間×単価（2026-10-27 決定）。実＝その人の工数 × 単価。

### 18.1 計算
メンバー x、月 m、契約 c:
```
plannedHours(x,c,m) = Σ_{a: a.memberId=x, a.contractId=c, a.startMonth<=m<=a.endMonth} a.allocation × standardHoursPerMonth
plannedCost(x,c,m)  = round(plannedHours(x,c,m) × 単価(x,m))        // §6 の単価。行(x,c,m)ごとに四捨五入
actualHours(x,c,m)  = 契約 c・月 m の CostLine のうち memberId=x の hours
actualCost(x,c,m)   = 同 CostLine の amount
```
- 契約期間外の月のアサインは数えない（`plannedHours = 0`。`CONTRACT_INVALID` の契約も同様）。
- メンバー月の合計 = Σ_c。`variance = plannedCost − actualCost`（正 = 計画より実績が少ない）。
- 稼働率 `utilization = actualHours / plannedHours`（分母 0 → null）。100% 超を赤にはしない（赤は §12 の 2 つだけ）。表示のみ。
- 未アサインの工数（アサインの無い契約に付けた工数）は `unplannedHours / unplannedCost` として別に持つ。
- メンバーの所属・役職・単価は §5 の有効レコード（当時の値）。所属チームは期間の終了月の値で表示し、月ごとの値は内訳に出す。
- `members.csv` に無いが工数のある ID も行に出す（名前は作業ログの `member_name`、`UNKNOWN_MEMBER` と同じ扱い）。
- 計算はコアに置く: `Model.memberMonths: MemberMonth[]`（x, m ごと。契約別の内訳 `byContract[]` を持つ）を `buildModel` で作り、画面は期間で合算する `aggregateMembers(model, scope)` を使う。

### 18.2 画面
- 一覧 `/members`: メンバーごとに 所属チーム・役職・計画時間・実績時間・稼働率・計画額・実績・差額。チーム絞り込みは「所属チーム（期間の終了月）」。検索欄。
- 詳細 `/member?id=`: 基本情報（所属の変遷）→ KPI（計画額・実績・差額・稼働率）→ 月次推移（計画と実績の時間）→ 契約別（計画・実績・差額。アサイン無しの契約は「アサインなし」チップ）→ 単価の変遷。
- 計画・実績の数値はすべて根拠ボタン（`allocation × 基準時間 × 単価`、CostLine）を持つ。
- 比較（計画・実績・差額・稼働率）の母集団は **経過月**（期間内で `m <= asOf 月`。§11 の消化率と同じ）。未来月には実績が無いので、期間全体の計画と比べると稼働率・差額が見かけ上よくなるため。期間全体の計画は KPI の補足と月次推移で別に示す。期間がすべて未来のときは期間全体（実績 0）で表示し、その旨を注記する。（2026-10-28 追記）

## 19. マスタ編集 `/masters`

対象: `data/masters/members.csv`（所属・役職・チーム）、`data/masters/rates.csv`（単価）、`data/masters/teams.csv`（チーム）、`data/targets.csv`（目標。§63）。アサイン（`data/assignments.csv`）と契約外予定（`data/outside-plans.csv`）はリソース計画 `/plan` で編集する（§36.1）。編集はリーダー層（GitLab の Developer 以上）だけが実際に保存できる。閲覧は誰でも可。

### 19.1 編集の考え方
- 履歴マスタ（§5）は **行を追加する** のが基本操作（「4月から単価変更」= 新しい `effective_from` の行を足す）。既存行の修正・削除もできるが、過去月の数値が変わる操作には確認ダイアログで「過去の計算結果が変わります（影響: N か月）」と出す。
- 確認ダイアログの「何が変わるか」は、過去の月で **実際に値が変わる列** に応じて出し分ける（一律に「実績・残予算など」と書かない）:
  - メンバーの `title`（役職）・単価の行 → 時間単価と、実績・残予算・消化率・着地見込み
  - メンバーの `team_id` → 所属チームによる組織別の集計（メンバー別の所属・チームでの絞り込み、チーム詳細・案件詳細の応援・ヘルプの区別。§72）。`division` / `department` / `section` → 事業本部・部・課の表示（§60）。`name` → 氏名の表示。`kind` → 区分の表示。これらだけの変更では「実績・残予算・消化率・着地見込みは変わりません」と明記する
  - チームの `parent_team_id` → 組織の木と上位組織の合計。`name` → チーム名の表示
  - アサイン → 着地見込み（アサイン方式）とメンバー別の計画
  - その月の有効な行が増える・無くなる（キー・適用開始月の変更、追加・削除）ときは、無い側を全列空として比べ、キー列（登録の有無）も変わったものとして扱う。`effective_from` だけが変わり値が同じ月は「変わる月」に数えない
- 保存前にブラウザ内で `parseDataset` + `validateDataset`（§14 と同じ）を編集後のデータに対して実行し、error があれば保存ボタンを押せない（理由を行に表示）。warning は表示のみ。
- 変更差分（追加・変更・削除の行）を保存前に一覧で見せる。
- CSV の書き出しは列順・改行コード（LF）・UTF-8（BOM なし）を固定し、変更していない行はバイト単位で元のまま残す（差分を最小にする）。

### 19.2 保存方式（config `masterEdit`）
```jsonc
"masterEdit": {
  "mode": "gitlab",           // "gitlab" | "download"
  "gitlab": {
    "apiBaseUrl": "",         // 例 https://gitlab.example.local/api/v4（空なら Pages の URL から推定しない。download に自動で落とす）
    "projectId": "",          // 数値ID または "group/project"
    "targetBranch": "main",
    "commitMode": "mr",       // "mr"（ブランチを作り MR を作成）| "direct"（targetBranch へ直接コミット）
    "tokenUrl": ""            // トークン作成画面（§78）。空 = GitLab の標準の場所、"/…" = GitLab 上のパス、"https://…" = そのまま
  }
}
```
- `gitlab` モード: 利用者が自分の Personal Access Token（scope `api`）を設定画面（§28）で登録する。トークンは `sessionStorage` にのみ保存し（タブを閉じると消える）、画面に再表示しない。`POST /projects/:id/repository/commits`（`actions[]` で複数ファイルを1コミット、各 action に `last_commit_id` を付けて競合を検出）。`mr` のときは `start_branch=targetBranch`、`branch=masters/<YYYYMMDD-HHmmss>-<user>` で新ブランチにコミットし、`POST /projects/:id/merge_requests` で MR を作る。結果画面に MR/コミットのリンクを出す。
- 競合（他の人が先に更新、HTTP 400 で last_commit_id 不一致）・権限不足（401/403）・ネットワーク/CORS 失敗は、それぞれ人が読める文で案内し、**編集内容を失わない**。CORS/ネットワーク失敗時は「CSV をダウンロードして GitLab 画面からアップロード」に切り替えるボタンを出す。
- `download` モード（または API が使えないとき）: 変更したファイルを CSV でダウンロードさせる。GitLab の Web IDE／ファイル画面でアップロードする手順は、保存の見出し横の「?」に入れる（§37）。
- ビルド時に `src/data/masters.json.ts` が各ファイルの生テキストと、そのファイルの最終コミットID（`git log -1 --format=%H -- <path>`。取れなければ null）を出す。編集の土台はこの生テキスト。
- 編集中の内容は `localStorage`（`yojitsu-navi:masters-draft:v1`）に下書き保存し、再訪時に復元を提案する。下書きは **「土台（生テキストと最終コミットID）＋差分（追加・変更・削除の行）」** として持つ。
- 土台が今のビルドと違う（他の人が先に更新した）下書きを復元するときは、「元データが更新されています」と示したうえで、下書きの差分を **最新の土台に当て直す**（rebase）。復元後の編集・保存・ダウンロードの土台は常に最新のビルドで、古い土台のまま保存・ダウンロードすることはない。
  - 当て直しは決定的な純粋関数で行う。下書きの土台と最新の土台の行を対応付け（同じ内容の行を順序を保って最長一致で対応させ、対応しない行は同じキー列の行どうしを対にする）、最新側で変わっていない行には下書きの変更・削除をそのまま当てる。追加した行は末尾に足す。
  - 下書きで変更・削除した行が、最新側でも変更・削除されていれば **衝突** とし、行ごとに「自分の下書き」と「最新のデータ」を並べて、どちらを残すか利用者に選ばせる（全部選ぶまで復元しない）。両方が同じ値に変えた・両方が削除した行は衝突にしない。
  - 当て直した結果を同じ土台でもう一度当て直しても結果は変わらない（冪等）。
- GitLab 保存が競合で止まったときは「他の人の更新がビルドされたあとに再読み込みすると、下書きを最新のデータに当て直して復元できる」と案内する。`download` モードでは、画面の元データのコミットIDを示し、GitLab 上のファイルがそれより新しければアップロードせずに再読み込みするよう案内する。

## 20. 本番 API の列名対応（取り込みアダプタの設定化）

本番の作業実績 API・所属データの仕様は本番でしか確認できないため、**コードを変えずに config だけで合わせられる** ようにする。

### 20.1 作業実績（`worklogSource.http` の拡張）
| 項目 | 意味 | 既定 |
|---|---|---|
| `columns.<field>` | 取得元の列名。ドット区切りで入れ子（`member.id`）。配列で複数候補（最初に値があるもの） | 現行どおり |
| `dateFormat` | `YYYY-MM-DD` / `YYYY/MM/DD` / `YYYYMMDD` / `ISO8601`（時刻付き。JST に変換して日付） / `epochMillis` | 自動判定（左から順に試す） |
| `hoursUnit` | `hours` / `minutes` / `seconds` | `hours` |
| `pagination` | `{ type: "none" }` / `{ type: "page", pageParam, sizeParam, size, startPage, stopWhen }` / `{ type: "offset", offsetParam, limitParam, limit, stopWhen }` / `{ type: "link" }`（`Link: rel="next"`）/ `{ type: "cursor", cursorPath, cursorParam }`。件数パラメータの省略・終了条件・上限は §90 | `none` |
| `query` | 追加のクエリ文字列（固定値）。`{from}` `{to}` `{fromDate}` `{toDate}` を置換 | 無し |
| `filters` | 取り込まない行の条件 `[{ column, equals | notEquals | in }]` | 無し |
| `encoding` | CSV 応答の文字コード（`auto` / `utf-8` / `shift_jis`） | `auto` |
| `members` | 取得対象の社員番号を API に渡す（§87）。`{ param, style: join / repeat, separator, chunkSize }`。社員番号はメンバーマスタから作る | 無し（渡さない） |
- 列が見つからないときはエラーで止め、**応答の最初の1行の列名一覧** を出す（設定ミスを見つけやすくする。値は出さない）。
- `npm run fetch -- --dry-run --sample=5` で、取得→変換結果の先頭 N 行と列の対応表を表示し、ファイルを書かない（本番での初回設定用）。
- 設定は `config.json`（コミットする）、トークンは環境変数のみ。
- 認証ヘッダはリダイレクトで別オリジンへ送らない（同一オリジンのリダイレクトだけ追う。別オリジンは中止）。ページング時も URL の既存クエリ文字列は書き換えず、ページ指定だけを足す。
- 取得行があるのに全行が対象期間外になる場合は、日付の読み違いとみなしてエラーで止め、月ファイルを書き換えない。期間外の行数はログに出す。
- 時間は分・秒から換算しても小数 4 桁まで保持して CSV に書く（行ごとに 0.01h へ丸めない）。

### 20.2 所属・役職の取り込み（`memberSource`）
所属部署・課・役職は人事系の元データから取り込む（2026-10-27 決定）。`memberSource` は `worklogSource` と同じ仕組み（`adapter: csv | http | none`、`columns`、`pagination` 等）で `memberId, name, kind, title, division, department, section` を取得し、`npm run fetch:members` で `data/masters/members.csv` を更新する。
- `team_id` は取り込まない（画面で手入力）。取り込み結果と現在の有効レコードを比べ、`name/kind/title/division/department/section` のどれかが変わった人だけ `effective_from = 取り込み実行月` の新しい行を追加する（`team_id` は直前の有効レコードを引き継ぐ）。変化が無ければ何もしない（冪等）。
- 取り込み元の氏名が空の人は、既存の氏名を空で上書きしない（件数を警告）。実行月より前の行が無い人（未来日付の行だけ）は、最も早い行を土台に実行月の行を足す。実行月より後の行は残すが、旧値をそのまま引き継いでいる項目は新しい値に揃える。
- 取り込みに無い既存メンバーは削除しない（不在の人の過去月を壊さない）。件数を表示する。
- `memberSource.adapter = "none"`（既定）の間は従来どおり手入力。マスタ編集画面は `memberSource.adapter != "none"` のとき取り込み対象列（`columns` に書いた列）を読み取り専用にする。社員番号・氏名は adapter によらず保存済みの行では読み取り専用（§81）。所属は既定では取り込まない（§81）。

# 3回目の追加仕様（2026-10-28）: 組織の種別・リーダー・リソース計画

範囲: 組織の種別（§21）、組織ごとのリーダー（§22）、リソース計画の入力（§23）。
画面文言を別ファイルにする作業（別スレッド）とは独立。ここで足す文言も同じ方式に従う。

## 21. 組織の種別（課・チーム・班など）

組織の段数や呼び名（本部・事業部・部・課・チーム・班・グループ…）は会社や時期で変わるため、**段（深さ）に固定の名前を付けず、組織ごとに種別を持たせる**。
- `teams.csv` に列 `level`（種別。自由入力の文字列）を追加する。省略可（列が無い・空の組織は種別なし）。
- 種別は §5 の履歴（`effective_from`）に乗る。「4月から第1課を第1部に格上げ」= 新しい行で `level` と `name` を変える。
- 親子関係は従来どおり `parent_team_id` で任意段数。同じ深さに違う種別が混ざってもよい（例: 課の下に班が直接ある組織と、課 › チーム › 班 の組織が並ぶ）。
- 種別の一覧は「その時点の組織で使われている `level` の値」から作る（別マスタは持たない。追加・改名は行を足すだけで済む）。マスタ編集の入力欄は既存の値を候補に出し（表記ゆれ防止）、新しい値も入力できる。
- 表示: チーム一覧・チーム詳細・パンくず・リソース計画の組織選択で、名前の横に種別を小さく出す。`TeamNode` に `level`（空文字 = なし）を持たせる。
- 集計の規則（§11・§16）は変えない。種別は表示と選択のための属性で、数値には影響しない。

## 22. 組織ごとのリーダー

- `teams.csv` に列 `leader_member_id`（リーダーの社員番号）を追加する。省略可・空可。組織ごとに 1 人。履歴（`effective_from`）に乗るので、リーダー交代は新しい行で表す。
- 兼務可（1 人が複数の組織のリーダーでもよい）。リーダーは配下の組織の所属でなくてもよい。
- 検証（§14 に追加）: `leader_member_id` が `members.csv` に無い → error `TEAM_UNKNOWN_LEADER`。
- 表示: チーム一覧に「リーダー」列、チーム詳細の見出しの下にリーダー名（期間の終了月時点。§16 の基準月）、リソース計画の組織選択。`TeamNode` に `leaderMemberId`（null = 未設定）を持たせる。
- 権限: 静的サイトのため「リーダー本人だけが自分の組織を編集できる」制御は画面では行わない。保存できるのは従来どおり GitLab の Developer 以上（§19）。リーダー欄は「誰が入力する担当か」を示す。

## 23. リソース計画の入力（リーダー → メンバー個人）

リソース計画 = 既存のアサイン（`data/assignments.csv`。人 × 契約 × 期間 × 配分人月）。新しいファイルは作らない。§10 の `assignment` 方式・§18 のメンバー別の計画は従来どおりこのファイルから計算する。
リソース計画の画面 `/plan`（§36.1。マスタ編集とは別の画面、保存の仕組みは共通）で、リーダーが自分の組織のメンバーをまとめて見ながら入力できるようにする。保存・下書き・検証・差分・影響月は §19 と同じ仕組み（アサインのファイルを編集する別の見せ方）。

### 23.1 表示
- 組織を選ぶ（木の順。名前・種別・リーダー名を表示。「すべて」も可）。URL `/plan?team=<teamId>` で開ける。URL に組織が無いとき（上部の「リソース計画」ボタンなど）は、ほかの画面のフィルタで選んでいる組織を引き継ぐ（未設定・すべては「すべて」。2026-10-31）。`&member=<memberId>` のときは、そのメンバーの基準月の所属組織を選び、その人の行を強調する。
- 期間 = 表の上の開始月〜終了月で選んだ月（1〜24 か月。既定は基準月から 12 か月。§71）。
- 行 = メンバー。対象は「期間のいずれかの月に、選んだ組織か配下に所属していた人」＋「選んだ組織か配下が担当する契約（`contract.team_id`）に、期間内の計画がある他組織の人（『応援』と表示）」。
- 各月のセル = その人のその月の配分合計＋契約外予定（人月、小数2桁。§36.3）。1.0 を超える月は「1.0 超」チップ（保守の配分だけで超えるときも警告。保存は止めない。§14・§40）とセルを黄、0 より多く 1.0 未満の月はセルを青系（§41）。赤は使わない（§12）。空き（1.0 − 合計）は合計列の補足に出す。
- 行を開くと、案件ごとの行と契約外予定の行（§36.3）。メンバーごとに「＋ 案件」（メンバーを入れた状態でアサインの追加ダイアログを開く）。
- 計算は純粋関数 `planView(sources, teamId|null, months)`（`src/core/plan.ts`）。編集中のデータ（保存前）で即時に計算し直す。

### 23.2 人月と時間の入力（2026-10-28 決定）
- **保存・管理・表示は人月に統一**。時間は入力のときだけ使える。
- アサインの追加・修正ダイアログの配分欄に「人月／時間」の切替を付ける。時間で入れた値は `allocation = 時間 ÷ standardHoursPerMonth`（既定 160h）で人月に直して保存する。入力欄の下に換算結果（例「16 時間 = 0.1 人月」）を出す。
- 換算した人月は小数 4 桁に四捨五入して書く（例 10h → 0.0625、1h → 0.0063）。末尾の 0 は書かない。
- 時間の基準は標準（`standardHoursPerMonth`）。月ごとの営業日（カレンダー基準）では換算しない（§18 の計画時間と同じ基準にするため）。

# 4回目の追加仕様（2026-10-28）: GitLab へのマージ方式・CSV 編集・設定画面

範囲: マスタ編集の保存を「CSV をダウンロードして GitLab にアップロード」から「画面内で編集 → GitLab にブランチと MR を作る → リーダーがこの画面でマージ」に変える（§24〜§26）、ヘッダーの件数バッジ（§27）、設定画面（§28）、試用のデモ（§29）。

## 24. 保存方式（§19.2 の変更）
- `masterEdit.mode` の既定を `gitlab` にする（`gitlab` | `download` | `demo`）。`commitMode` の既定は従来どおり `mr`。
- 保存 = 編集した各ファイルを **新しいブランチに 1 コミット** し、**MR（マージリクエスト）を作る**。本体（`targetBranch`）に入るのはマージされたときだけ。
- `download`（CSV をダウンロードして GitLab の画面でアップロード）は、接続できないとき（CORS・ネットワーク失敗、接続先が未設定）の **退避手段** としてだけ残す。画面の主な流れには出さない。
- `direct`（`targetBranch` へ直接コミット）は互換のため残すが推奨しない。§26 の保護ブランチ設定では GitLab が拒否する。
- トークンの登録は設定画面（§28）だけで行う。保存欄はトークンが無いとき保存ボタンを無効にし、「GitLab のトークンが未登録です。設定へ」のリンクだけを出す（§37）。

## 25. CSV で直接編集（表／CSV の切替）
各ファイルのタブに「表で編集」「CSV で編集」の切替を付ける。行単位の操作（ダイアログ）に加えて、まとめて書き換える・Excel から貼り付けることができる。
- CSV 編集欄には今の編集結果（`serializeMasterDoc` の出力）を出す。書き換えて「反映」を押すと、表の編集と同じ文書（`MasterDoc`）に取り込む。反映するまでは表・検証・差分・下書きは変わらない。
- Excel からの貼り付け（タブ区切り）も受け付ける。1 行目（見出し）にタブがあればタブ区切りとして読む。
- 見出し行は今のファイルと **同じ列名の集合** でなければならない（順序は違ってよい。ファイルの列順に並べ直して取り込む）。足りない列・知らない列・重複した列があれば反映しない。閉じていない引用符も反映しない（行番号を示す）。
- 取り込みは純粋関数 `docFromCsvText(doc, text)`（`src/core/csvEdit.ts`）。元ファイルの行との対応付けは §19.2 の当て直しと同じ規則:
  1. 内容（trim した値）が同じ行を、順序を保って最長一致で元の行に対応させる（その行は「変更なし」。引用符の付け方などは元のまま書き戻す）
  2. 対応しなかった行は、キー列（と適用開始月／開始月）が同じ元の行と順に対にする（=「変更」）
  3. 残りは「追加」、どの行とも対にならなかった元の行は「削除」
- 反映後の件数（追加・変更・削除）を示す。取り込んだ結果は §19 の検証・差分・影響月の対象になる（保存できるかは表で編集したときと同じ）。
- メンバーの CSV 編集はできない（表で編集する。社員番号・氏名と取り込み列を書き換えさせないため。§81）。

## 26. マージ待ちの変更（MR 一覧とマージ）
マスタ編集画面の上部に「マージ待ちの変更」を出す（`gitlab`・`demo` で、トークンがあるとき）。
- 対象 = `targetBranch` 向けで開いている MR のうち、ソースブランチが `masters/` で始まるもの（この画面で作った MR）。`GET /projects/:id/merge_requests?state=opened&target_branch=<targetBranch>&per_page=100` を画面で絞る。
- 各 MR: タイトル、作成者、作成日時、検証（MR のパイプラインの状態。あれば）、マージできるか。「内容を見る」で、そのMRで変わる行を §19 の差分と同じ形（追加・変更・削除、変わった列）で出す。差分は MR の `diff_refs.base_sha` と `head_sha` の各マスタファイルを取得し、§25 の対応付けで求める（GitLab の行差分より読みやすいため）。
- **マージは特定のリーダー層だけ**: 権限の判定は GitLab に任せる（画面では強制できない）。MR の `user.can_merge`（`GET /projects/:id/merge_requests/:iid`）が true の人にだけ「マージ」ボタンを出し、それ以外の人には「マージはリーダーが行います」と出す。
  - GitLab 側の設定（docs/DEPLOY_GITLAB.md）: `targetBranch` を保護ブランチにし「Allowed to merge = Maintainers」「Allowed to push = No one」。リーダー層 = Maintainer、編集する人 = Developer。
- マージ: `PUT /projects/:id/merge_requests/:iid/merge`（`sha` に表示中の head を付け、見ている内容と違う変更がマージされないようにする。ソースブランチは削除）。確認ダイアログで変更件数を示してから実行する。
  - 失敗の案内: 405/406（競合・マージできない状態・パイプライン待ち）、409（内容が更新された → 一覧を読み直す）、401/403（権限）、ネットワーク。
  - 成功後: 「CI が画面を作り直したあと（数分）に数値に反映されます」と出す。
- 取り下げ: 作成者本人またはマージできる人は MR を閉じられる（`PUT …/merge_requests/:iid` `state_event=close`）。
- 一覧は画面を開いたとき・保存して MR を作ったとき・マージ／取り下げのあと・「更新」ボタンで読み直す。

## 30. 作業種別と契約外の工数（2026-10-28）

作業実績には「どんな作業をしたか」（作業種別。列 `task`）が入っている。これを使って、
1. 保守契約外の仕事（提案・運用設計など）を契約の実績から外す、
2. 1 人・チーム・顧客ごとの工数を **契約内（運用保守）／契約外** に分けて見せる（人員配置・組織体制の検討用）、
3. 実績が見込みを超えたときに、作業種別ごとの内訳で原因を追えるようにする。
アサイン・リソース計画（§10・§18・§23）は作業種別を持たない（従来どおり人 × 契約 × 配分人月）。

### 30.1 作業種別の分類表 `data/task-types.csv`
| 列 | 内容 |
|---|---|
| `task` | 作業実績の作業種別（照合は §4.1 の `normalizeName` で正規化して完全一致。`match=含む` の行は部分一致 §62.2） |
| `category` | `運用保守` または `運用保守以外`（旧表記の `契約内` / `契約外`、英字の `contract` / `outside` も可。§50.5） |
| `note` | 任意のメモ |

- ファイルが無い・行が無いときは、すべての作業を契約内として扱う（従来と同じ。警告も出さない）。
- 分類表に無い作業種別（空欄を含む）は **契約内** として数え、警告 `TASK_UNCLASSIFIED`（作業種別ごとに 1 件、時間・件数）を出す。登録すれば消える。

### 30.2 計算
- 顧客名なしの除外（§4.2-1）・hours/日付の不正行の無視は、分類より先に従来どおり行う。
- **契約外** の作業ログは、契約の実績（`cost`・`hours`・消化率・着地見込み・メンバー別の実績 §18）に **入れない**。
  - 紐付けルール（§4.2）に当たれば「関連契約」として覚える（参考表示用）。当たらなくても未紐付け警告は出さない（未紐付け警告は契約内の作業だけ）。
  - 契約外は予算の外なので **金額は出さず、時間と人月だけ** を扱う。
- 契約内の作業ログは従来どおり（§4〜§7）。
- 工数の明細 `WorkRow`（画面用に `data/work-hours.json` で別に配る）: （月, メンバー, 契約ID|null, 顧客, 作業種別, 区分）ごとに
  - `hours` = 時間の合計
  - `amount` = 契約内のみ。契約・月・メンバーの実績行（CostLine）の金額を作業種別ごとの時間で **最大剰余法で按分**（円の整数。作業種別の合計が契約の実績と 1 円単位で一致する）。契約外は `null`。
  - 顧客 = 契約に紐付いたものは契約の顧客名、紐付かない契約外は作業ログの顧客名（§17 の `customerKey` で束ねる）。
  - 所属チーム（`teamId`）= その月のメンバーの所属（§5 の有効レコード）。
- 人月 = 時間 ÷ `standardHoursPerMonth`（§18 と同じ標準基準）。

## 31. 名称で選ぶ・リソース計画のセル編集（2026-10-28 要望）

### 31.1 ID を前面に出さない
- メンバー・案件（契約）・組織の ID は画面の本文に出さない。名前（案件は「顧客 / 案件名」、同じ案件の契約は期間で区別）で表示する。
  ID は内部キー（URL・CSV・Excel 出力・検索の一致対象）としてだけ使う。

- 計算根拠の表の契約列は「顧客 / 案件名」と契約期間。データ確認画面の不備の説明（存在しない ID など）は ID のまま出す。
- パートナーの会社名は表示しない（ダミーデータの氏名からも外す）。

### 31.2 候補から選ぶ入力欄（コンボボックス）
- メンバー・案件・組織・単価のキーは、文字を打つと候補が絞り込まれる入力欄で選ぶ（数百件を想定）。
  - 一致: 全角・半角、大文字・小文字を区別せず、空白で区切った語をすべて含むもの。名前の先頭一致を上に。メンバーは所属・役職、案件は顧客名でも引ける（ID でも引けるが表示はしない）。
  - 候補は最大 50 件を表示し、残りは件数だけ示す。↑↓で移動、Enter で決定、Esc で閉じる。
  - 候補に無い文字のまま離れたら、直前に選んでいた値に戻す（単価のキー＝役職名は新しい値も入れられる）。
- 組織の選択肢は名前（種別）だけ。ID は出さない。

### 31.3 アサインは案件を選ぶ
- アサインの追加・修正では契約ではなく **案件（顧客 × 案件名）** を選ぶ。保存時に期間の各月をその案件の契約へ割り当て、CSV には従来どおり `contract_id` を書く（ファイル形式は変えない）。
  - 月 m の契約 = その案件で m を含む契約（複数なら開始月が最も遅いもの）。どの契約にも入らない月は、m より前に終わった最後の契約、無ければ m より後に始まる最初の契約。
  - 連続する同じ契約の月をまとめて 1 行にする。期間が契約の切り替わりをまたぐときは複数行に分けて保存し、確認画面で知らせる。
  - 契約が見つからない（ファイルに無い契約 ID の）既存行は、その ID のまま表示し、選び直すまで変えない。

### 31.4 リソース計画のセル
- メンバー行は 1 行（名前＋所属を小さく）に詰め、行の高さを抑える。
- 月のセルにマウスを載せる（キーボードではフォーカスする）と、その月の内訳（案件ごとの人月と時間・合計・空き）を吹き出しで出す。
- セルをクリック（Enter）すると、その場で修正できる小さな編集欄を開く。
  - その月に掛かる計画ごとに人月の入力欄、新しい案件を足す行（案件を選ぶ＋人月）を出す。
  - 反映範囲: 「この月だけ」（既定）／「この月以降」（既存の行は行の終わりまで、新しい行は表示中の期間の終わりまで）。前回の選択を覚える。
  - 保存すると、行を月で分けて書き直す（例: 4〜3月 0.5 の 6 月だけ 0.3 → 4〜5月 0.5・6月 0.3・7〜3月 0.5）。0 か空にした月は計画から外す。
    同じメンバー・契約で隣り合い、配分が同じ行は 1 行にまとめ直す（元に戻せば元の 1 行に戻る）。
  - 過去の月（計算基準月以前）に影響するときは §19 と同じ注記を出し、もう一度押して確定する。
  - Esc・外側のクリックで閉じる（変更は捨てる）。計算は純粋関数（`src/core/plan.ts` の `contractSegments`・`editMonthAllocation`・`mergeAdjacent`）。

### 31.5 役職はプルダウンで選ぶ（2026-10-31 試用版のコメント）
- メンバーの追加・修正の「役職」はプルダウン。選択肢は「（なし）」、単価マスタ（`rates.csv`）の役職のキー（ファイルの並び）、メンバーに書かれている役職の順。役職マスタは作らない。
- 新しい役職は、単価に役職の行を追加すると選べる（注記は欄の下の 1 行）。候補に無い値が入っている既存行は、その値のまま選ばれた状態で出す。
- CSV で直接編集（§25）では従来どおり自由に書ける。

## 35. 不在（退職・休職など。`members.csv` の `status` 列）

実運用では退職・休職・育休・パートナーの契約終了などでいなくなる人がいる。過去の月の実績と単価は残したまま、いなくなった月から「在籍していない」と分かるようにする。
理由はパターン化しない（いないことが分かれば目的は足りる。想定外の理由で直さずに済むよう）。画面・文言は一律「不在」。

- `data/masters/members.csv` に任意の列 `status` を足す。空・`在籍`・`active` = 在籍、それ以外は何が書いてあっても、その行の `effective_from` の月から不在（`退職`・`休職`・`契約終了` など、書いた値はそのまま残す）。列が無いファイルもそのまま読める。
- 不在は **行を追加** して表す（§5 の履歴の決まりどおり）。例: `M141,…,T4111,2026-01,退職`。所属チーム・役職は直前の値を書いておく（最後の所属として表示する）。
  復帰・再入社は、後の月に `status` が空の行を足す。
- **不在になった月の稼働**: 不在になった月（前月は在籍）は、その月に計画（アサイン・運用保守以外の予定）か作業実績があれば稼働とみなす（月の途中で退職・休職に入る場合）。
  計画も実績も無ければその月から稼働しない。翌月からは稼働しない（`isWorkingAt`）。
  画面には作業実績のある月を `model.json` の `worklogMonths`（`"memberId|YYYY-MM"`）で渡す（マスタ編集中に不在の月を変えても判定できるよう、不在の月に絞らない）。
- 計算: 不在の月も作業実績があれば実績に入れる（データを捨てない）。単価は直前の行の役職・個人単価を使う。
- 検証（警告。保存・公開は止めない）:
  - `WORKLOG_AFTER_LEFT`: 不在になった月より後の作業実績がある（付け間違いの可能性）
  - `ASSIGNMENT_AFTER_LEFT`: 不在になった月より後に掛かるアサイン（計画）が残っている。不在になった月の計画は稼働なので警告しない
- 画面:
  - メンバー一覧・詳細: 名前の横に「不在 YYYY年M月」のチップ。詳細の所属は「不在（最後の所属: ○○）」、所属の変遷に在籍の列（在籍／不在）。
  - リソース計画: 稼働しない月はその組織の所属に数えない（人数 × 1.0 にも数えない。§58）。不在になった月より後に計画が残っていれば行に「不在中の計画 Nか月」の警告チップ、稼働しない月のセルは斜線。
  - マスタ編集: メンバーの表・行の編集に「在籍」（在籍／不在）。CSV に理由が書いてある行は、その値を保ったまま「不在」と表示する。名前を選ぶ候補では不在の人を後ろに並べ「不在」と添える。
- 人事データの取り込み（§20.2）: 在籍状態は取り込みで変えない。取り込み元に無い人を不在にしない（取り込み元の範囲が分からないため）。
  不在の人が取り込み元に載っていても在籍に戻さない（休職中の人も載るため）。復帰は画面か CSV で在籍の行を足す。
- グラフ: 値がすべて 0（不在の期間など）のときも棒を全高にしない（目盛りを 0〜既定の幅で描く）。

## 36. 対象ごとの 1 行と変更の履歴（2026-10-28 要望）

「同じ対象が複数行あると、対象の一覧なのか変更の一覧なのか分からない。アサインは変更が多い」への対応。**画面の持ち方だけを変え、CSV の形式（1 行 = 適用開始月の値、または 1 期間）は変えない**。

### 36.1 マスタ編集とリソース計画の役割
- **マスタ編集 `/masters` = 台帳**: メンバー・単価・組織（いつから何の値か）。ほかに一覧の「案件」「祝日」（§80）と「目標」（§63）。タブは 6 つ。
- **リソース計画 `/plan` = 人 × 案件 × 月の配分**: アサイン（`data/assignments.csv`）と契約外予定（`data/outside-plans.csv`）。タブは無い 1 画面。
- 旧 URL `/masters?view=assignments` / `?view=plan` は `/plan` へ転送する。
- 保存（下書き・検証・差分・GitLab への MR）は 2 つの画面で共通。別の画面で編集した変更も同じ保存に入り、保存欄に「n 件の変更（別の画面で編集）も、同じマージリクエストに入ります」とその画面へのリンクを出す。
- 同じタブで 2 つの画面を行き来したとき、土台が変わっていなければ下書きの「復元 / 破棄」を聞かずに続きから表示する（別のタブ・後日に開いたときだけ聞く）。

### 36.2 台帳（メンバー・単価・組織）
- 1 行 = 1 つの対象（キー: member_id / key / team_id）。先頭の列は名前（メンバー・組織）か単価のキー。値は **基準月（計算基準月）に有効な値**。基準月にまだ始まっていない対象は最初の値と「YYYY年M月から」。
- 基準月より後の変更は値の下に「YYYY年M月〜 新しい値」、行に「予定 n」。
- 「変更の履歴」ボタンで、その行の下に適用開始月ごとの履歴を開く: 「登録 / 変更 / 値の変わらない履歴」「いまの値 / 予定」、前の履歴から変わった列は「前 → 後」。履歴ごとに「修正・元に戻す・削除」。エラーのある対象は自動で開く。
- 「＋ 変更」: その対象の最新の値を写したダイアログ。適用開始月の既定は基準月の翌月（最新の履歴がそれより後ならその翌月）。過去に影響すれば §19.1 と同じ確認。
- 「＋ 新しいメンバー／単価／組織」: 新しい対象の登録。
- 純粋関数: `ledgerGroups`・`nextChangeOf`（`src/core/ledger.ts`）。

### 36.3 リソース計画（人 × 案件）
- 1 行 = 1 人（月のセル = 保守の配分 ＋ 契約外予定の合計）。「案件 n（＋契約外）」で開くと、**案件ごとに 1 行**（契約が更新で分かれていても案件でまとめる）と「契約外予定」の 1 行。
- 案件・契約外予定の行の「＋ 変更」: 変える月（既定は基準月の翌月）・人月（人月／時間）・いつまで（計画の終わりまで〔既定〕／この月だけ／終わりの月を指定）。画面が期間を分けて CSV の行を書き直す（`replaceRange`）。
  - 期間の外は変えない。期間の中は指定の値。0 はその期間の計画を外す。期間の各月の契約は §31.3 の割り当て。
  - 同じ契約・同じ値で隣り合う行は 1 行にまとめ、空いた行 ID を使い回す（元に戻せば差分なし）。同じ月に重なる行があるときは変えずに「変更の履歴で重なりを直して」と案内。
  - 「計画の終わりまで」= その月以降に掛かる計画の最後の月。無ければ案件の契約の終わり、それも無ければ表示中の期間の終わり。
  - プレビュー: 「YYYY-MM〜YYYY-MM を 0.90 → 0.50 人月にします」「…の計画を外します」「…に 0.30 人月の計画を入れます」。過去の月に及ぶときは §19.1 と同じ確認。
- 「変更 n件」で開く変更の履歴: 期間・人月・種類（開始／再開／前 → 後 に変更／契約の更新／同じ人月が続く／重なり／月の誤り）と「YYYY-MM から 計画なし」。項目ごとに「修正・元に戻す・削除」。純粋関数 `periodHistory`。
- セルの編集欄（§31.4）にも契約外予定の欄を出す（同じ月に重なる行があるときは無効）。
- 表の上に「名前・所属・案件で絞り込み」（空白区切りの語をすべて含む人。全角半角・大文字小文字を区別しない）。合計行は絞り込んだ人の分。数百人の組織で人を探すため。

### 36.4 契約外予定 `data/outside-plans.csv`（§30.5 の具体化）
- 列: `member_id, start_month, end_month, person_months, note`（note は任意）。ファイルが無い・空・見出しだけなら「契約外予定なし」（エラーにしない）。画面で初めて保存するときは GitLab に新規作成（`action: create`）。
- 検証（error）: 存在しないメンバー（`OUTSIDE_UNKNOWN_MEMBER`）、月の形式（`INVALID_MONTH`）、開始 > 終了（`OUTSIDE_PERIOD_INVERTED`）、人月が 0 以上の数値でない（`OUTSIDE_OUT_OF_RANGE`。1.0 超は受け付ける）、同じ人の同じ月に複数行（`OUTSIDE_OVERLAP`、重なりごとに 1 件）。1 行の人月が 1.0 超は警告（`OUTSIDE_OVER_1`。保存はできる）。
- 保守の配分との合計が 1.0 を超えても保存は止めない（人の行に「1.0 超 n か月」チップ。赤は使わない）。予算・実績・着地見込み・計画額には入れない。表の下に「うち契約外予定」の月合計。

## 39. 本番 GitLab の構成と権限（2026-10-29 要望）
展開を迷わず進められるよう、社内 GitLab 側の構成・権限・ファイルの置き場をこのリポジトリで決め、確認・適用を自動化する。推奨構成と手順の正は `docs/DEPLOY_GITLAB.md`。
- 構成: グループ `yojitsu-navi` の下にプロジェクト `yojitsu-navi`（どちらも Private）1 つ。コード・データ・CI・Pages を同じプロジェクトに置く。メンバーはグループに追加する。
- ブランチ: `main` は保護ブランチ（直接プッシュ = No one、マージ = Maintainers、force push 不可）。画面の保存は `masters/<日時>-<ユーザー>`（§19.2）、定期取り込みは `data/<種類>-<日時>` の MR を通す。
- 権限: 閲覧 = Guest、編集（MR 作成）= Developer、マージ = Maintainer（リーダー層）、管理 = Owner。トークンは各自の PAT（scope `api`）と、取り込み用の Project Access Token（Maintainer・`write_repository`、CI/CD 変数 `GIT_PUSH_TOKEN` は Protected・Masked）。

### 39.1 接続先を GitLab CI から補う
- `config.json` の `masterEdit.gitlab.apiBaseUrl`・`projectId` が空のとき、ビルド時の環境変数 `YOJITSU_GITLAB_API_URL`・`YOJITSU_GITLAB_PROJECT` で埋める（`src/components/gitlab-env.js`）。`.gitlab-ci.yml` の build ジョブが `CI_API_V4_URL`・`CI_PROJECT_PATH` を渡すので、社内 GitLab では config を書き換えずに保存先がそのプロジェクトになる。
- config に値があればそちらを優先する。`mode` が `demo`・`download` なら補わない。マスタ編集のローダとヘッダーのバッジ（§27）は同じ結果を使う。
- 環境変数はローダの入力の指紋に入れる（接続先が変わればキャッシュを捨てる）。

### 39.2 設定の確認・適用 `npm run gitlab:setup`
- `scripts/gitlab-setup.ts`。既定は確認だけ（GET のみ）で、推奨値との違いを ✓／✗ で出す。`--apply` で自動で直せる項目を直し、確認し直す。2 回目以降は何も変えない（冪等）。
- 確認する項目: 公開範囲 Private、Pages = Only Project Members、CI/CD = Only Project Members、パイプライン成功時だけマージ、マージ後にソースブランチを削除、既定ブランチ = `targetBranch`、保護ブランチ（上記）、Maintainer 以上がいるか、スケジュールがあるなら `GIT_PUSH_TOKEN`、トークン系の CI/CD 変数が Protected・Masked か。後ろの 3 つは手で直す項目（直し方を出す）。
- 保護ブランチは Free 版の API では中身を直接変えられないため、違うときは外してから推奨値で保護し直す。
- トークンは環境変数 `GITLAB_TOKEN` だけで受け取る（`--token` は拒否）。接続先は `--api`・`--project`、無ければ config、それも空なら `CI_API_V4_URL`・`CI_PROJECT_PATH`。終了コード 0 = 推奨どおり、1 = 直すところが残る、2 = 引数・接続の誤り。

### 39.3 接続の確認で設定の不足を出す（設定画面 §28）
「接続を確認」で、ユーザー・権限に加えて次を調べ、不足があれば「GitLab の設定に N 件の不足があります」と一覧で出す（警告。説明は増やさない）。
- `GET /personal_access_tokens/self` の scopes に `api` が無い → scope。
- `GET /projects/:id` の `visibility` が `private` でない → visibility。`pages_access_level` が `public` → pagesPublic。
- Maintainer 以上の人だけ `GET /projects/:id/protected_branches/:targetBranch`: 404 → unprotected、push に 0 より大きいレベル → pushAllowed、merge に 40 未満のレベル → mergeByDeveloper。個人・グループ指定（`access_level` が null）は判定しない。
- 取れない項目（古い GitLab に無い API、権限で読めない、通信失敗）は警告しない。デモの模擬は推奨どおりの値を返す。

### 39.4 定期取り込みは MR で反映する
`main` が直接プッシュ不可なので、`fetch-worklogs`・`fetch-members` は変更を `data/<種類>-<日時>` に 1 コミットして push し、push オプション（`merge_request.create`・`target`・`merge_when_pipeline_succeeds`・`remove_source_branch`・`title`）で MR の作成と、パイプライン成功後の自動マージを指定する（`scripts/ci/push-data-mr.mjs`）。変更が無ければ何もしない。
- CI の重複を避けるため、`.gitlab-ci.yml` の `workflow:rules` で、開いている MR があるブランチへの push は MR のパイプラインだけにする。

## 40. 検証の一覧（2026-10-29 要望）
「1.0 超過はエラーにしないで警告に」「エラーを探すのがしんどい。名前で教えて、押したら該当箇所に飛んでほしい。色も警告と分けて」への対応。マスタ編集・リソース計画の「検証」の欄。
- **1.0 人月超は警告**（`ALLOCATION_OVER_1`。§14）。保存を止めない。同じ人の続いた月は 1 件（例「2026-11〜2026-12 のアサイン合計が 1.0 を超えています（最大 1.4）」）。

## 44. アプリ全体を npm パッケージで社内に持ち込む（2026-10-29 要望）
「この仕組みを npm パッケージで社内に持ち込む」への対応。社内は外部（開発元のリポジトリ）に接続できない前提で、`.tgz` のファイル 1 つから社内 GitLab のプロジェクトを作り、Pages まで流せるようにする。画面は変えない。
- パッケージ名 `yojitsu-navi`（コマンド `yojitsu-navi`）、置き場 `packages/app/`。**依存を持たない**（Node の標準モジュールだけ）ので、`npm install -g` や `npx` で入れるときに外部へ接続しない。版はルートの `package.json` と同じ値にする（違うと `npm run app:pack` が止まる）。
- 中身: `template/` = git が管理するファイル一式（`.github/` を除く。`.gitignore` は `_gitignore` として入れ、`init` で戻す）、`bin/`・`lib/` = コマンド、`dist/gitlab-setup.mjs` = `scripts/gitlab-setup.ts` の型を外した JS（依存なしで §39.2 の確認・適用ができる）。`template`・`dist`・`deps` と `.tgz` は git に入れない。
- **依存の扱い（決定）**: 2 種類を作る。社内に npm のミラーがあれば依存なし版（約 8 MB。うち画面フォント約 4 MB §46、CI は `NPM_CONFIG_REGISTRY` で取る）。無ければ依存込み版（`--with-deps`、約 64 MB）で、`package-lock.json` の依存を npm のキャッシュとして `deps/npm-cache/` に入れ、`init` が `vendor/npm-cache/` に写す。`.gitlab-ci.yml` はこのフォルダがあれば `npm ci --offline --cache vendor/npm-cache` する。キャッシュには Linux x64 と Windows x64 の両方の OS 別バイナリ（esbuild・rollup）を入れる（Runner・PC がどちらの OS でも `npm ci` できる。§79）。理由: 社内のミラーの有無が未確認で、どちらでも止まらないようにするため。node_modules をそのまま入れる案は OS ごとのバイナリが合わず採らない。
- **計算コアとの関係（→ §84 で変更。1 つのパッケージにまとめた）**: `@yojitsu-navi/core`（§43）は別パッケージのまま残す（monorepo の 2 パッケージ）。core はほかのプロジェクトが `import` して使う部品、`yojitsu-navi` は予実ナビのプロジェクトを作る道具で、使う人と更新の仕方が違うため。`yojitsu-navi` の template には `packages/core/` も入るので、社内でも §43 の手順で core を公開できる。
- **個人・会社の情報を入れない**: 社内 GitLab の URL・グループ名・個人名・アカウント名はパッケージに入れない（`template/config.json` の接続先は空）。接続先は社内で `init --gitlab <URL> --project <グループ/プロジェクト>` のときに入れる（`config.json` の `masterEdit.gitlab` と `git remote` の 2 か所。省くと聞かれ、空でも §39.1 のとおり CI が補う）。利用者が設定画面で入れるのは自分のトークンだけ。
- `yojitsu-navi init [フォルダ]`: 空のフォルダに一式を写し、`.yojitsu-navi.json`（入れた版と各ファイルの SHA-256）を書き、`git init -b main`・最初のコミットまで行う。push は利用者が行う（外部に出す操作なので）。
- `yojitsu-navi update [フォルダ]`: `data/` と `config.json` は足しも消しもしない。それ以外は新しい版に入れ替え、前の版の記録にあって新しい版に無いファイルは消す。前の版の記録と中身が違う（社内で手を入れた）ファイルがあれば、何も変えずに止まる（→ §91）。`config.json` に無い新しい設定の項目と、サンプルにだけある新しいデータのファイル（`data/worklogs/` は除く）も知らせる。結果はブランチ `update-<版>` にコミットし、MR でマージする（§39 の保護ブランチのまま）。コミットしていない変更がある・古い版にする・依存込みのプロジェクトを依存なし版で更新する、のときは止まる（`--force` で続ける）。上書きするファイル・残すファイルの区分、差分の確認とバックアップは §91。社内の CI・npm の設定の置き場（`.gitlab-ci.local.yml`・`.npmrc`）は §91.1、更新後に出す導入先で行うこと（`CHANGELOG.md`）は §91.2。利用環境の `package.json` の名前は `yojitsu-navi-site`（§91.3）。
- `yojitsu-navi migrate-ci [フォルダ]`: 社内で `.gitlab-ci.yml` に書いたランナーのタグ・変数・社内だけのジョブを `.gitlab-ci.local.yml` に移す（§91.4）。
- `init`・`update` の最後に、CI 定義が使うファイルがそろいコミットされているか・GitLab が受け付けない書き方が無いかを確かめる（§85・§91.3。`yojitsu-navi check`、プロジェクトの中では `npm run ci:check` でも確かめられる）。
- `yojitsu-navi upgrade`（`update` からビルドまでを 1 回で）・`reset-data`（サンプルのまま残ったデータを空に）・`update` の `--no-commit`・`--summary`・`--log` は §94。
- `yojitsu-navi gitlab-setup [--apply]`: §39.2 と同じ。接続先は `config.json`、空なら `git remote` の `origin`（https）から読む。トークンは `GITLAB_TOKEN`、無ければ画面に出さずにその場で聞く（Windows のコマンドプロンプトでも使えるように。引数では受け取らない）。
- 手順は `docs/DEPLOY_GITLAB.md`（手順 0〜2、「新しい版にする」）。
- **画像を入れない**（2026-10-31 要望「画像はリポジトリにどうしても必要な場合を除いて不要。npm 化で無駄に大きくなる」）: リポジトリに画像を置かない（例外はファビコンの `src/icons/` だけ §89。フォントは画像ではないので対象外）ので template にも入らない。`npm run app:pack`・`core:pack` は中身に画像があると止まる（依存込み版の `deps/` は外部の npm パッケージなので見ない）。リポジトリ全体の検査は `tests/unit/docs-links.test.ts`（拡張子と先頭のバイト）。置いてよい画像は `scripts/lib/image-detect.mjs` の `IMAGE_ALLOWLIST` に理由つきで書き、リポジトリの検査と npm パッケージの検査が同じものを使う。

## 50. 運用保守以外の作業の計画と予実（2026-10-29 要望）
「契約に紐付かない作業（提案・構築・設計・会社業務など）も管理対象にし、計画時に入れたい。予実は含む／含まないを切り替えたい」への対応。§30.5・§36.4 を種別つきに広げる。

### 50.1 運用保守以外の種別
- 種別は作業種別の分類表 `data/task-types.csv`（§30.1）で管理する。任意の列 **`group`**（計画の種別）を足し、契約外の行で「どの種別の予定として数えるか」を書く（例: 提案・見積 → 提案、運用設計 → 設計、社内会議 → 会社業務）。空・列なしは `task` の表記をそのまま種別にする。契約内の行の `group` は使わない。
- 種別の一覧 = 契約外の行の種別（正規化して重複を除き、ファイルの順。`outsideTypes`）。作業実績の無い種別（例: 構築）も行を置けば計画に使える。
- `data/outside-plans.csv` に任意の列 **`type`**（種別）を足す。空 = 種別なし（旧形式のファイルの行はすべて種別なし。画面で開くと見出しの末尾に `type` を足す）。
- 検証: 同じ人・**同じ種別**・同じ月に複数行 → error `OUTSIDE_OVERLAP`（種別が違えば同じ月に並べてよい）。分類表に契約外の種別があるのに一覧に無い種別 → warning `OUTSIDE_UNKNOWN_TYPE`（保存は止めない）。人の月の合計（保守の配分 ＋ すべての種別）が 1.0 を超える月は従来どおりチップだけ。

### 50.2 顧客名の無い運用保守以外の作業
- 契約外に分類した作業は、顧客名が空でも除外しない（会社業務など）。工数の明細（§30.2）に顧客「顧客名なし」の契約外として入り、工数画面・メンバー別に出る。
- 契約内（未分類を含む）の顧客名なしは従来どおり除外し、`EXCLUDED_NO_CUSTOMER` を出す。

### 50.3 リソース計画（§36.3 の変更）
- 人の行を開くと、案件ごとの行のあとに **運用保守以外の種別ごとの行**。出すのは **その人に、表示中の期間（§71）の計画か実績がある種別だけ**（2026-10-31 依頼者「全員が全部やるわけじゃない。作業の種類は多い人で年 100 を超える」）。計画 = outside-plans.csv の行（保存済みの行も含む。編集中に消しても保存までは行を残し、履歴から戻せる。月の不正な行も出す）、実績 = 作業実績のうち運用保守以外に分類された作業（`model.outsideWorkMonths` = 「社員番号|月|種別」）。並びは分類表の順、一覧外の種別はその後。分類表に運用保守以外の種別が無ければ、セルの編集欄は従来どおり種別なしの 1 欄。
- ほかの種別は、セルの編集欄の **「作業を追加」**（案件と同じ検索付きの候補。種別には「運用保守以外」を添える。もう出ている種別は候補から外す）で選び、人月を入れて足す。
- 種別ごとの「＋ 変更」「変更 n件」、セルの編集欄も種別ごとの欄。行の追加・修正のダイアログでは種別を検索付きの候補から選ぶ。
- 表の下の「うち契約外予定」はすべての種別の合計。

### 50.4 予実の「運用保守以外を含む」切替（メンバー別・メンバー詳細）
- フィルタバーの「運用保守以外を含む」（URL `outside=1`。既定は含まない＝URL に書かない。localStorage にも覚える）。メンバー別 `/members` とメンバー詳細 `/member` に置く。
- 含むとき、**計画にも実績にも** 契約外を足す（片方だけに足すと差額・稼働率がずれるため）。
  - 計画 = 契約外予定の人月 × 基準時間（`standardHoursPerMonth`）× 単価。実績 = 契約外の作業時間 × 単価（§6 と同じ単価。メンバー・月・種別ごとに円に丸める）。
  - 種別は §4.1 の `normalizeName` で正規化して突き合わせる（全角・半角、大文字・小文字の違いは同じ種別の 1 行。表示名は最初に出てきた表記）。検証・リソース計画と同じ扱い。
- 選べる期間（`meta.minMonth`〜`meta.maxMonth`）は、契約の期間に **運用保守以外の予定・実績の月** を足した範囲。契約が終わった後の月の予定（翌年度の会社業務など）もメンバー別で選べる。
  - 契約外の作業時間は種別（47.1 の `group`）ごとに束ね、同じ種別の予定と比べる。予定の無い種別の実績は「計画なし」（アサイン外と同じ扱い）。
  - 契約外予定だけ・契約外の作業だけの人も一覧に出る。
  - メンバー詳細の「案件別」に「運用保守以外: 種別」の行（案件詳細へのリンクなし）。根拠パネルにも同じ行。作業ログの明細は契約ごとのファイルなので契約外の行には出さない。
- 予算の画面（全体サマリー・チーム・顧客・案件）には置かない。契約外には予算が無く、実績だけ足すと残予算・超過見込みが実態より悪く見えるため（契約の予算・実績・着地見込みは常に契約内だけ）。
- データ: `MemberMonth.byContract` に契約外の行（`contractId` = `~outside:<種別>`、`outsideType`）。`MemberMonth` の月の合計は契約内だけ（従来と同じ）。`aggregateMembers({ includeOutside })`・`memberMonthlySeries(…, { includeOutside })` の既定は false。

## 61. 今月の進捗（日別の速報。2026-10-30 要望）

- 計算（`src/core/daily.ts` の `dailyProgress` / `progressFromDays`）:
  - 今月の上限 `cap` = 対象の案件の asOf 月の予算の合計 × `capRatio`（既定 1）。チーム・顧客・案件の詳細では、目標（§63）のうち期間（開始月〜終了月）が asOf 月を含むものがあれば `capRatio` = 1 − 目標の残予算率（`targetForMonth`。複数あれば期間の最も短いもの = 月ごとの目標を年度の目標より優先、同じ長さなら終了月の早いもの）。全体には目標が無いので予算のまま。目標を使うときは KPI の補足に「目標の残予算率 n%（予算の m%）」（目標がマイナスなら m > 100%。上限が予算を超える）、根拠に予算・目標の残予算率と式を出す（2026-10-30、目標の取り込み後につないだ）。
  - 営業日は §9 と同じ（土日・holidays。行の無い年は国民の祝日で補う `HolidaySet`）。経過した営業日 = 1 日〜`lastDate` の営業日の数。残りの営業日 = 今日（§75）から月末までの営業日。ただし `lastDate` より後だけ（今日の分まで取り込んでいれば明日から）。
  - 目安（日ごと）= cap × その日までの営業日 ÷ 月の営業日。今日までの目安 = cap × 経過した営業日 ÷ 月の営業日。
  - 今日までの実績 = 1 日〜`lastDate` の実績額の合計（休日の作業も入る）。残り = cap − 実績。残りの 1 日あたり = 残り ÷ 残りの営業日（0 日なら —）。
  - これまでの 1 日平均 = 実績 ÷ 経過した営業日（0 日なら —）。このペースの月末 = 実績 + 平均 × 実績がまだ無い営業日（`lastDate` より後。取り込みが止まった日も平均で延ばす）。取り込みが毎日あれば「残りの営業日」と同じ。
- 表示: KPI 4 枚（今月の上限／今日までの実績（目安超え・目安内）／残り n 営業日の予算（2026-10-30 試用版のコメントで「で使える」から改名。1 日あたり・これまでの平均）／このペースの月末（上限超え・上限内））。数字を押すと式と値の根拠。金額は単位に従い、百万円のときだけ小数 2 桁（KPI・グラフ・表の画面表示。Excel は円）。グラフは累計（速報）の実線・月末見込み（このペースの月末）の点線（凡例も点線。凡例の破線・点線は幅 22px の背景の繰り返しで描く。2px の border では実線に見えた、2026-10-30）・目安の破線（青）・上限の破線（赤）、土日・祝日の背景、マウスで日ごとの実績・累計・目安。下に「表で見る」（日ごとの実績・時間・累計・目安、Excel 出力）。説明は見出しの「?」だけ。
- チーム詳細だけ、その下に「メンバーごとの今月の時間」（`dailyMembers`）: 行 = このチームの案件に今月の作業実績か今月のリソース計画がある人（計画の多い順、同じなら時間の多い順）。列 = 名前（横に送っても固定）・累計（時間）・計画（今月の `assignmentPlan` の時間 = 配分 × 基準時間の合計。無ければ —）・残り/日（(計画 − 累計) ÷ 残りの営業日。計画を超えたら赤の「超過」、計画なし・残り 0 日は —）、その右に今月の日ごとの時間（濃さ 4 段階。土日・祝日は背景、経過前は空）。名前はメンバー詳細へのリンク。

## 63. チーム・顧客・案件の目標（2026-10-30 要望）
「各チームごとに目標値を設定できるか。いつにどの値を目指す、みたいな」「チームでも、顧客でも案件でも」への対応。指標は残予算率だけ（2026-10-30 決定。実績額・稼働の目標は持たない）。

### 63.1 データ `data/targets.csv`（省略可）
| 列 | 内容 |
|---|---|
| `target_type` | `team` / `customer` / `project` |
| `target_id` | チームID / 顧客名（§4.1 の正規化で照合）/ 契約ID |
| `end_month` | 終了月 |
| `remaining_rate` | 目標の残予算率（%。`20` = 20%。`20%`・全角も可。100 以下。マイナス可で、超過している対象の改善目標（例: 残予算率 -100% を -50% に）に使う。`-50` のほか `−50`・`▲50`・`△50` も負の数） |
| `start_month` | 開始月（任意。空 = 終了月を含む年度の最初の月） |
| `note` | メモ（任意） |

- 1 行 = 1 件。同じ対象に終了月の違う目標を何件でも置ける（上期・通期など）。月ごとの目標は `start_month = end_month`。同じ対象・同じ終了月の 2 行目は `TARGET_DUPLICATE`（エラー）。
- 検証: 種類の誤り `TARGET_INVALID_KIND`・対象が空 `TARGET_MISSING_ID`・月の形式 `INVALID_MONTH`・開始月 > 終了月 `TARGET_PERIOD_INVERTED`・率 `TARGET_RATE_INVALID` はエラー。対象が見つからない（チームの廃止・案件の削除）は `TARGET_UNKNOWN`（警告。画面には出さない）。
- 数値の計算（予算・実績・着地見込み）には使わない。今月の進捗（§61）の「今月の上限」だけは、今月を含む目標があれば 予算 ×（1 − 目標の残予算率）にする（`targetForMonth`）。

### 63.2 判定（`src/core/targets.ts` の `evaluateTarget`）
```
期間      = start_month（空なら終了月を含む年度の最初の月）〜 end_month
対象の案件 = team: 基準月の組織で配下を含む担当案件（§11 と同じ）/ customer: 顧客名が同じ案件 / project: その契約
予算      = Σ 期間内の月の予算
着地      = Σ 実績（基準月より前の月）＋ 終了月までの見込み（§10 と同じ式。方式は画面の「着地見込み」）
残予算率   = (予算 − 着地) ÷ 予算      （予算 0 → 「予算なし」）
判定      = 終了月 < 基準月 → 達成 / 未達（実績で確定）、それ以外 → 達成見込み / 未達見込み
            残予算率 ≥ 目標 なら 達成（見込み）
```
- 画面の期間（表示条件）には左右されない（目標の期間で数える）。方式を変えると見込みの判定は変わる。

### 63.3 画面

## 75. 「今日」は開いている人の今日（日本時間）（2026-10-31 要望）
「データの取り込みは毎日成功するとは限らない。今日を基準に判断したい。今日（日本時間）と、データがいつ時点かは分けて考える」への対応。

- **今日** = 画面を開いている人の今日（Asia/Tokyo。UTC+9・夏時間なし。端末のタイムゾーン設定に依らない。`src/core/calendar.ts` の `todayJst`）。計算基準日 `asOf` はこの日で、基準日に依る計算・表示はすべてこれに従う: 月の状態（確定・速報・未来）と確定済みの最新月（§5）、年度と期間の既定・プリセット（今月・先月・今後 3 か月。§34）、着地見込みの実績月と残り月（§10・§54）、消化率の経過月（§11）、組織の基準月、リソース計画の表示する月（§71）、今月の進捗の対象の月と残りの営業日（§61）。
- **データの時点** = 作業実績の取得日時（`meta.worklogFetchedAt`。上段の「作業実績の取得」・ページ見出しの下）。今日とは別に従来どおり出す。実績・予算の値は取り込んだ作業ログから作るので、今日が進んでも変わらない。
- 仕組み: 画面は静的なページで、ビルドは取り込みが成功したときだけ走る（`.gitlab-ci.yml`）ので、ビルドした日は取り込み成功日になる。そこで `model.json` を読んだ直後に `rebaseModel(model, viewerAsOf(meta))`（`src/core/rebase.ts`。画面の入口は `src/components/layout.js` の `loadModel`・`withToday`）で、作業ログ明細の要らない値（meta・月の状態・着地見込み・リソース計画の明細・組織の木）を今日で計算し直す。その日にビルドした Model と同じ値になる。
  - `viewerAsOf`: `meta.asOfFixed`（ビルドで `YOJITSU_AS_OF` を指定した）ならビルドの値のまま。それ以外は日本時間の今日。ただしビルドした日より前には戻さない（端末の時計のずれ対策。リソース計画の明細はビルドした月からしか無い）。
  - **`YOJITSU_AS_OF` はテスト・試用版のデモ用に残す**（E2E は固定した日で期待値を作る）。本番のビルドでは指定しない。
  - `scripts/build.ts` はローダの日付を揃えるため `YOJITSU_AS_OF` を必ずローダに渡すので、呼び出し側が固定したかは `YOJITSU_AS_OF_FIXED`（`1`/`0`）で別に渡す（`scripts/lib/inputs.ts` の `isAsOfFixed`。入力の指紋にも入れる）。
- 案件詳細の作業ログ明細（`data/worklogs/*.json`。ビルドした日の状態を持つ）の「状態」列は、今日に置き換えた Model の月の状態で出す（明細と月次の表で確定・速報が食い違わない）。
- 今月の進捗（§61）: 対象の月は今日の月。`daily.json` が前の月のもの（月が替わってから取り込みが無い）なら今月の実績 0 として出す。グラフに今日の位置を縦の点線（「今日」）で出す。取り込みが止まると累計の線が今日の手前で終わるので、説明文を足さずに見分けられる。
- **取り込みが止まっているとき**: 最後の取得日（日本時間）が今日の前日より前なら、「作業実績の取得」の日時を警告色・太字にし、title に「作業実績の取り込みが止まっています（実績はこの日時まで）」（`isWorklogStale`。毎日の取り込みが朝でも夜でも、1 回抜けたら出る）。取得したことが無ければ従来どおり「未取得」。
- 文言: ページ見出しの下の「計算基準日」を「今日」に、データ確認の補足も「今日 YYYY-MM-DD」に改名。計算ルール・使い方に今日と取得日時の違いを書いた。
- 再発防止: `tests/integration/rebase.test.ts`（同じ月の数日後・翌月の確定日の前後・2 か月後・翌年度で、置き換えた Model がその日にビルドした Model と同じ／元の Model を変えない／実績・予算・取得日時は変わらない／`viewerAsOf` の日本時間・固定・時計のずれ／`isWorklogStale` の境目）、`tests/unit/daily.test.ts`（残りの営業日は今日から・取り込みが止まった日の月末見込み・月初で実績なし）、`tests/e2e/today.spec.ts`（固定しないビルドの `model.json` を日本時間の翌月の日付で開くと、今日・今月のプリセット・今月の進捗の月が今日になり、取得日時が警告色になる）。

## 76. 体制図（チーム一覧の表示切替。2026-10-31 要望）

管理者層が予実を見ながら体制を考えるときに、組織とメンバー、計画と実態（実績）を 1 枚で見たい、への対応。**現状を見せるだけ**で、ここからマスタ・計画は編集させない（編集はマスタ編集・リソース計画の GitLab マージ方式 §24 のまま）。名前は「体制図」（検討・編集を連想させる名前にしない）。

- 置き場所: チーム一覧 `/teams` の見出しの右に「表 / 体制図」の切り替え。新しいページ・タブ・メニューは増やさない。URL に `view=chart`（体制図）・`month=YYYY-MM`（表示する月）・`color=gap`（色の基準）を持つ（既定値は URL に書かない）。
- 月: 「◀ 月 ▶」と、データの最初の月〜最後の月のスライダー（離したときに描き直す）。既定は表と同じ組織の基準月 `min(期間の終了月, 今月)`。組織はその月の組織（§5）。
- 描き方: 組織の入れ子の枠（本部 › 事業部 › 課 › チーム › 班）。各組織の見出しに 名前・種別・リーダー・配下を含む人数（前月との差）・その月の残予算率（今月以降は選んだ着地見込みの方法の見込み原価で計算。マイナスは赤 §67）。見出しを押すとチーム詳細へ。

  - 色「計画」（既定）: その月の計画（案件のアサイン＋運用保守以外の予定）の合計人月。1.0 超 = 黄、1.0 = 緑、1.0 未満 = 青系（§41）、計画なし = 地。チップに人月。
  - 色「計画とのずれ」: 確定した月だけ、`planGapKindOf`（§64 と同じ。16 時間以上かつ ±30%）で 実績が多い = 黄・少ない = 青系・ずれなし = 緑。チップに差の時間。未確定の月は色を付けず、その旨を 1 行出す。

- 応援・ヘルプ（§72）: 案件の主担当チーム（配下・上位を含む）の外の人が、その月にその案件へ計画か実績を持つと、主担当チームの枠に「応援」（所属チームあり）・「ヘルプ」（所属チームなし・マスタ未登録）のチップで載せる。計画が無く実績だけの人は「実績だけの応援・ヘルプ n人」に畳む（スポットの作業で組織の人が埋もれないように）。
- 吹き出し（カーソル・フォーカスで出す）: 組織 = その月の担当顧客（配下を含む、案件数の多い順に 12 社まで）と予算・実績（見込み）・残予算率・人数。メンバー = 案件・運用保守以外ごとの実績と計画（今月以降は「計画（見込み）」、未来の月は計画だけ）、応援先、前月の所属・今月の所属（抜けた人）。

## 79. Windows・Linux のどちらでも動く（2026-10-31 依頼者）
社内の GitLab Runner は Windows。Linux に変わることもあるので、ビルド・テスト・取り込み・公開はどちらの OS でも同じに動かす。
- `.gitlab-ci.yml` の `script` は `node scripts/ci/*.mjs`・`npm run`・`npx vitest` だけにする。sh と PowerShell で意味が変わる書き方（`if`・`$変数` の展開・`find`・`gzip` など）は Node のスクリプト（`scripts/ci/`: `install`・`e2e`・`pages`・`publish-core`・`fetch-data`・`push-data-mr`）に入れ、変数は `variables:` で渡す。`tests/unit/ci-portable.test.ts` で検査。

| `deepmerge`（low・Framework 経由。`@rollup/plugin-node-resolve`・Framework も同じ 1 件として数えられて 3 件） | マージ結果のオブジェクトのプロトタイプ汚染 | ビルドのときに Framework が自分の設定を合わせるだけで、外からの入力を渡さない。修正版がまだ無い。`npm audit fix --force` は Framework を 1.10 に**下げる**ので採らない | 修正版か Framework の新しい版が出たら上げる |

- 非推奨の警告（`npm warn deprecated`。脆弱性ではない）: `inflight`・`glob@8`（`@rollup/plugin-commonjs` 25 経由）、`whatwg-encoding`（`jsdom` 23 経由）。どちらも Framework 1.13 が版を決めていて、上げると Framework の作りが変わる（commonjs は 29 で `glob` を使わなくなったが、Rollup の設定の互換を確かめていない）。動きには影響しないので Framework の新しい版を待つ。
- 確かめ方: 開発元・利用環境どちらでも `npm audit`・`npm ls <パッケージ>`。`npm audit fix --force` は使わない（上の理由）。利用環境で `overrides` を消すと 7 件に戻る。

### 84.3 依存のインストールスクリプト（2026-11-05 導入先のレビュー指摘）
npm 12 から、依存の `preinstall`・`install`・`postinstall` は `package.json` の `allowScripts` で許可したものだけが動き、ほかは止めて `install scripts blocked because they are not covered by allowScripts` と知らせる。依存の中でスクリプトがあるのは `esbuild`（`postinstall: node install.js`）だけ。
- `esbuild` の `postinstall` は、OS ごとの本体（`@esbuild/win32-x64` など。`optionalDependencies` で入る）が入っているかを確かめ、速く起動できるよう置き換えるだけ。止めても本体は入るのでビルドは動く（npm 12 で止めた状態でビルドできることを確かめた）。
- 推奨: `package.json` に `"allowScripts": { "esbuild": true }`（版を付けない書き方。`npm install-scripts approve esbuild` は版を付けて書くので、`esbuild` を上げるたびに書き直しが要る）。npm 11 以前は `allowScripts` を読まず、これまでどおりすべて動く。`package.json` は `update` で新しい版になるので、社内で書き足さない。
- 社内の `.npmrc` で `ignore-scripts=true` にしているなら、`allowScripts` に関わらずスクリプトは動かない（それでもビルドは通る）。依存込みのパッケージ（`vendor/npm-cache`）は組み立てのときにスクリプトを動かさずに作る。
- 依存を足して新しくスクリプトがある部品が入ったら、中身を確かめてから `allowScripts` に足す（`npm install-scripts ls` で一覧）。

## 86. 作業実績が案件の実績に入るかの判定（まとめ。2026-11-03 依頼者）
導入先のレビュー「未登録の作業・契約期間の判定など、集計の正確さに関わる仕様を明確に」への対応。§4・§30・§62 に分かれていた判定を 1 か所にまとめる（挙動は変えない）。

### 86.1 判定の順序
ビルドのたびに、取り込み済みの**全期間**の作業実績に対して計算し直す。過去月も、mapping.csv・contracts.csv・task-types.csv を直せば結果が変わる。

1. **無視**: 時間が数値でない・0 以下、日付が不正（`YYYY-MM-DD` でない・存在しない日）の行。どこにも入れない（データ確認の検証に件数）。
2. **運用保守以外か**（§30・§62）:
   - 作業ログの (顧客, 案件) のルール（3. と同じ探し方）に作業名のキーワードがあれば、どれかの行に合う → 運用保守、どれにも合わない → 運用保守以外。
   - キーワードが無ければ task-types.csv（完全一致 → 含む）。表に無い作業は運用保守として扱い、`TASK_UNCLASSIFIED` 警告。
   - 運用保守以外は案件の実績に入れない（メンバー別・稼働実績で別に数える。§50）。
3. **顧客名が空**（運用保守の作業）: 除外（`EXCLUDED_NO_CUSTOMER`）。
4. **ルール**: 作業コードの行（§92）があればそのコードの行。無ければ (顧客, 案件) の完全一致（§4.1 の正規化後）→ 無ければ (顧客, "")。行に期間（§92）があれば、作業日の月が入る行だけを使う（どれも入らなければ未紐付け `RULE_OUT_OF_PERIOD`）。完全一致の行が 1 行でもあれば、期間に合う契約が無くても (顧客, "") には回さない。どちらも無い → 作業名から抜き出した案件名（§97。設定があるとき）→ それも無い → 未紐付け（`NO_RULE`）。
5. **候補の契約**: キーワードのある行があれば合った行の契約、無ければそのキーの全行の契約（作業コードの行はキーワードを使わない）。指す契約が存在しない・不備で除外中なら未紐付け（`UNKNOWN_CONTRACT`・`EXCLUDED_CONTRACT`）。別の契約には回さない。
6. **期間**: 作業日の**月**が契約の開始月〜終了月に入る契約（日では見ない）。
   - 1 件 → その契約。
   - 0 件 → 未紐付け（`OUT_OF_PERIOD`）。
   - 2 件以上 → 契約ID昇順の先頭に入れ、`MAPPING_AMBIGUOUS` 警告（データ確認の「計算時の警告」）。
7. 紐付いた行の金額 = 時間 × その月の単価（§6・§7）。

### 86.2 未紐付けの扱い
- 実績にも着地見込みにも入れない（金額 0）。データ確認の「未紐付けの作業実績」に (顧客名, 案件名, 理由) でまとめ、時間・件数・最初と最後の日を出す。`npm run validate` は警告だけで、取り込み・ビルドは止めない。
- **案件の割り当ては人が mapping.csv に書く**。作業名のキーワードは「どの作業が運用保守か」と、同じ (顧客, 案件) の行が複数あるときに「人が書いた行のどれに入れるか」を決める（§62.1）。mapping.csv に無い案件をキーワードで自動で決めることはしない（依頼者の方針）。
- 例外は §97: 作業名から抜き出した案件名が contracts.csv の案件名と**完全一致**する、または人が登録した別名に一致するときだけ自動で紐付ける（2026-11-05 依頼者「完全一致ならやる」）。曖昧一致はしない。

### 86.3 契約の更新（同じ顧客名・案件名の作業が続く）
- mapping.csv に同じ (顧客, 案件) の行を新しい契約IDで 1 行足す。旧契約の行は消さない。作業日の月が契約期間に入る方へ紐付く（6.）。
- 旧契約と新契約の期間が重なる月は `MAPPING_AMBIGUOUS`（契約ID昇順の先頭）になる。契約期間が重ならないように直す。
- 既存の行の契約IDを書き換えると、過去月の実績は旧契約から外れる。新しい契約の期間に入る月は新しい契約へ移り、入らない月は未紐付け（`OUT_OF_PERIOD`）になって実績から消える。過去の対応を残すには、書き換えずに行を足す。

### 86.4 導入先のレビューとの差（§92 で対応）
- 作業コードでの紐付け、mapping.csv の行ごとの期間、期間の重なりの事前検証（`npm run validate` の警告）、未登録の作業コード・作業名の変更の検出、検出したときに取り込みを止める設定は §92 で足した。
- 案件をキーワードだけで自動で決めることはしない（依頼者の方針）。未登録の作業コードは一覧に出し、人が mapping.csv に書く。作業名の案件名の完全一致・登録した別名による紐付けは §97。

## 87. 作業実績 API の取得対象をメンバーマスタから作る（2026-11-03 依頼者）
本番導入先の社内レビューの指摘への対応。取得する人は 100 人を超える見込みで、社員番号をメンバーマスタと API 設定の両方で持たない。
- **対象者はメンバーマスタ（`data/masters/members.csv`）から作る**。`worklogSource.http.members` を設定したときだけ、取得する期間（既定は直近 `refetchMonths` か月）に **1 か月でも在籍している人** を対象にする。期間の最初の月に不在になった人（前月は在籍）も入れる（不在した月の実績を拾うため。§35）。区分（社員・パートナー）・チームの有無（ヘルプ、§72）は問わない。入社前・不在後の期間には入れない。社員番号を API の設定に書く項目は作らない。
- **複数人をまとめて 1 リクエストで取る**: `param=A,B,…`（`style: join`、区切りは `separator`、既定 `,`）か `param=A&param=B`（`style: repeat`）。`url`・`query` に `{members}` と書けばその位置に入る。`chunkSize` 人（既定 50）ずつに分けて順に取る。ページング（§20.1・§90）は 1 回ごとに効く。
- **過去の実績の取り直し（退職者・異動者を含む）**: 期間を指定すると、その期間の在籍者が自動で対象になる（今は退職・異動していても、その期間にマスタで在籍なら入る。異動は所属が変わるだけで社員番号は同じなので対象のまま）。
  - `npm run fetch -- --from YYYY-MM --to YYYY-MM`: その期間の月ファイルを全員分で書き直す。
  - `--members 社員番号,…` を足すと、その人の行だけを差し替え、ほかの人の行は残す（マスタに無い人・不在の期間の人も指定できる）。この取り直しでは `_meta.json` の取得日時を変えない（全員分の取得ではないため）。
  - GitLab では Build > Pipelines > Run pipeline で変数 `FETCH_FROM`・`FETCH_TO`（必要なら `FETCH_MEMBERS`）を入れて実行する（`fetch-worklogs` ジョブが動く）。CI/CD 変数には登録しない（毎日の取り込みが同じ期間になるため）。
- **途中で失敗したら既存の CSV を書き換えない**: どの回のリクエストが失敗しても（再試行後の 4xx・5xx・ページ上限・列の欠落など）全体を失敗にし、月ファイルを 1 つも書かない（全部取れたときだけまとめて差し替える。従来の `writeFilesAtomic`）。人事の取り込み（§20.2）も同じ（members.csv を書かない）。
  - 失敗は記録して **データ確認画面の「データの検証」に警告で出す**: 作業実績は `data/worklogs/_meta.json`、人事は `data/masters/_members-meta.json` の `lastFailure`（日時と理由。トークンは伏せ、300 文字まで）。作業実績の取得日時（`fetchedAt`）は前回成功のまま。次に成功すると消える。
  - CI（`scripts/ci/fetch-data.mjs`）は失敗の記録だけを MR にしてからジョブを失敗で終える（GitLab の通知も出る）。`--dry-run` の失敗は記録しない。
- `members` を設定しない API はこれまでどおり（社員番号を渡さず全件を取る）。
- 実装: `scripts/lib/fetch-targets.ts`（対象者・分割）、`scripts/lib/fetch-status.ts`（失敗の記録）、`scripts/adapters/http.ts`、`buildRequestUrl`（`scripts/adapters/http-source.ts`）。再発防止: `tests/integration/member-targets.test.ts`。

## 90. ページングを連携先 API に合わせる（2026-11-03 依頼者）
連携先 API の実測: ページ番号だけを受け付け、件数のパラメータを付けると HTTP 400。終わりは空配列が返るまで。§20.1 の `page` は件数を必ず付け、設定件数未満で終わるため取得できなかった。作業実績・人事（`memberSource.http`）の両方に効く（同じ取得処理）。
- `page` の `sizeParam`、`offset` の `limitParam` は省略可。省略（または空文字）なら件数のパラメータを付けない。
- 終了条件 `stopWhen`（`page` / `offset`）: `short` = `size` / `limit` 未満の行数で終了（既定。従来どおり）、`empty` = 0 行のページで終了。`short` のとき、および件数のパラメータを付けるときは `size` / `limit`（1 以上の整数）が必須。件数を付けずに `short` にするなら API 側の 1 ページの件数を書く。`offset` は返った行数だけ進める。
- 連携先の設定例: `{ "type": "page", "pageParam": "page", "stopWhen": "empty" }`（接続先の値は `config.json` に書き、リポジトリの既定値は変えない）。
- 無限取得の防止: `maxPages`（既定 5000〈2026-11-03 依頼者、当初 1000〉、1 以上の整数）を超えたらエラーで止め、月ファイル・members.csv を書き換えない（途中までのデータで実績が少なく見えるのを防ぐため、警告で続行はしない）。失敗はデータ確認画面の「データの検証」に警告で出る（§87）。従来の「2 行以上のページが以前と同じ内容」の検出は `empty` でも効く（空配列を返さず最後のページを繰り返す API で止まる）。
- 設定の誤り（`size` 不足・`stopWhen` の値違い・`maxPages` が 0 以下）は通信の前にエラー。
- 既存設定（`stopWhen` 無し・件数パラメータあり）の送るパラメータ・終了位置・結果は変えない（`tests/unit/api-adapter.test.ts`「既存のページング設定は従来どおり」、property テストで新旧の結果一致）。

## 91. 更新でローカルの変更を守る（2026-11-03 依頼者。導入先のレビュー指摘）
「更新で上書きするファイルと保持するファイルを明確に定義し、ローカルの変更があれば上書き前に検出して警告。可能なら更新前の差分確認とバックアップ」への対応。§44 の `update` は社内で変えたファイルを上書きしてから一覧で知らせていた（MR の差分で気づく前提）が、上書きの前に止めるようにする。
- **区分**（`packages/app/lib/project.mjs` の `fileKind`。表は `docs/DEPLOY_GITLAB.md`「新しい版にする」）: 残す＝`config.json`・`data/` 以下すべて（足しも消しもしない）、および パッケージにも前の版の記録にも無いファイル（社内で足したもの）。入れ替え＝`vendor/npm-cache/`（依存込みのとき）。コマンドのもの＝`.yojitsu-navi.json`・`.yojitsu-navi-backup/`。それ以外でパッケージに入っているもの（`.gitlab-ci.yml`・`package.json`・`src/`・`scripts/`・`docs/` など）は上書き、前の版の記録にあって新しい版に無いものは削除。
- **検出**: `.yojitsu-navi.json` の SHA-256（コマンドが入れたときの中身）と今の中身を比べる。上書き・削除するファイルが「中身が違う」「記録に無いのに同じ名前である」のどちらかなら、**何も変えずに止まり**（終了コード 2）一覧を出す。改行が CRLF になっただけ（Windows の `core.autocrlf`）は変えたことにしない。記録にあるのに無くなっていたファイルは、git の除外設定でコミットされなかったもの（§85）と見分けられないので、止めずに入れ直す。`--force` でもこの確認は飛ばさない。
- **選び方**: `--overwrite` は新しい版にする。`--keep-local` は社内の版を残し、記録の `kept` に入れて次の `update` でも止まらずに残す（残したことは毎回一覧に出る。`--overwrite` で新しい版に戻せる）。2 つは同時に指定できない。
- **差分の確認**: `--dry-run` は何も変えず（コミットしていない変更・古い版でも止まらない）、変更・追加・削除の一覧と、社内で変えたファイルの差分（`git diff --no-index`。`-` が社内の今、`+` が新しい版）を出す。git が無ければ一覧だけ。
- **バックアップ**: 上書き・削除する前のファイルを毎回 `.yojitsu-navi-backup/<年月日-時分秒>/`（ローカル時刻。ロケールによらず、Windows で使えない文字を使わない。同じ名前があれば `-2` を付ける）に写し、前の版の `.yojitsu-navi.json` も入れる。git には入れない（`.gitignore`。古い版の `.gitignore` でも入らないよう、`update` の `git status`・`git add` はこのフォルダを除く）。
- 理由: 上書きしてからの一覧では、MR を見落とすと社内の CI 定義などの直しが消えたまま本番に入る。`config.json`・`data/` 以外を「社内で変えてよいファイル」として一律に残すと、新しい版の直し（CI の参照先など）が入らず動かなくなるため、ファイルごとに選ぶ形にした。
- 再発防止: `tests/integration/app-package.test.ts` の `update`（止まる 3 種類・無くなっていたファイルは入れ直す・何も変えない・`--dry-run` の差分・`--overwrite` のバックアップ・`--keep-local` が次の版でも残る・CRLF・区分・コマンドの終了コード）。

### 91.3 GitLab が受け付ける CI の設定にする・プロジェクトの中から確かめる（2026-11-05 依頼者。導入先のレビュー指摘）

## 92. 作業コードでの紐付けと、未登録の作業コードの検出（2026-11-03 依頼者。導入先のレビュー指摘）
「契約の増減で作業コードの追加・作業名の変更が頻繁に起きる。キーワードに合うのに mapping.csv に無い作業コードを、作業名・初回日・最終日・工数とともに見たい。作業名の変更・キーワードの一致状況の変化も見つけたい。見つけたときに警告か処理停止かを選びたい」「契約の更新後も同じ作業コードを使い続けるとき、期間の違う案件に対応付けたい。重なり・一意に決まらないときは検証と警告。終わった案件・過去の対応を残したまま新しい案件を足したい」への対応。案件の割り当ては人が行う（キーワードで自動で決めない）。本番の作業実績には作業コードの列がある（依頼者）。

### 92.1 データ
- 作業実績の任意列 `task_code`（作業コード）。`data/worklogs/YYYY-MM.csv` には、作業コードのある行がその月に 1 行でもあれば最後の列に書く（無ければ従来どおりの列だけ）。API は `worklogSource.http.columns.taskCode` を設定したときだけ読む。値の無い行は列ごと省かれることがあるので、応答のどれか 1 行にあればよい（どの行にも無ければ列名の打ち間違いとして止める）。
- mapping.csv の任意列 `task_code`・`start_month`・`end_month`。列が無い・空なら従来どおり（期間なし＝全期間）。
  - `task_code` を書いた行は**作業コードの行**: 顧客名・案件名は使わない（空でよい。メモとして書いてもよい）。キーワード（`task_include` / `task_exclude`）も使わない。
  - `start_month` / `end_month`（`YYYY-MM`、片方だけも可）は、その行を使う期間。作業日の月で判定する。名前の行にも書ける。
- 作業コードは照合前に NFKC・前後の空白を除く・英字を大文字にそろえる（`normalizeCode`）。

### 92.2 紐付け（§86.1 の 4. を変更）
- 作業コードの行があるコードの作業は、名前の行より先にその行で探す。顧客名が空でも紐付く。行の期間に入らない月は未紐付け（理由「対応表の期間外」`RULE_OUT_OF_PERIOD`。名前の行には回さない）。
- 作業コードの行の無いコードの作業・作業コードの無い作業は、従来どおり名前の行で探す。
- 作業コードの行がある作業は、人が案件に割り当てたものなので運用保守として扱う（§62 のキーワードに合わなくなっても、分類表で運用保守以外の作業でも、運用保守以外に回さない。キーワードの行が 1 行も無くても同じ）。
- §62 のキーワードの振り分けも、名前の行のうち作業日の月に掛かる行のキーワードで決める（期間ごとにキーワードを変えられる）。掛かる行が無い月は全行のキーワードで決め、紐付けは「対応表の期間外」になる。
- 契約の更新: 同じ作業コードの行を新しい契約IDで 1 行足し、旧契約の行の `end_month`・新契約の行の `start_month` で分ける（契約期間が重ならなければ期間は省いてもよい）。旧契約の行は消さない。
- 未紐付けの一覧・警告は、作業コードの行で探したものは作業コードごとにまとめ「作業コード X」と出す。

### 92.3 検証（`npm run validate`）
- `MAPPING_MONTH_INVALID`（error）: `start_month` / `end_month` の形式不正。`MAPPING_PERIOD_INVERTED`（error）: 開始月 > 終了月。
- `MAPPING_PERIOD_OVERLAP`（warning）: 同じ探し方（同じ作業コード、または同じ顧客・案件・キーワード）の 2 行が、行の期間と契約期間の重なる月に別の案件を指す（作業がその月に来ると一意に決まらない）。キーワードの違う名前の行は §62 の振り分けなので対象外。
- `MAPPING_OUTSIDE_CONTRACT`（warning）: 行の期間が契約期間と 1 か月も重ならない（その行は使われない）。
- 実際に一意に決まらなかった作業は、従来どおり計算時に `MAPPING_AMBIGUOUS`（契約ID昇順の先頭）。
- ダミーデータでは、将来開始の C180 が同じ名前の C150 と 2026-12〜2027-03 で重なり `MAPPING_PERIOD_OVERLAP` が 1 件出る（実績が出る前に分かる例）。

### 92.4 作業コードの点検（`config.json` の `taskCodeCheck`）
- `include`（運用保守の作業名に含むキーワード。どれか 1 つ）、`exclude`（含むと対象外。含むより優先）。照合は §62 と同じ（`normalizeKeyword` の部分一致）。`include` が空・設定なしなら点検しない。

### 92.5 取り込み時の動作（`onUnregistered` / `onChange`）
- `warn`（既定）: 取り込み、`npm run fetch` のログに警告を出す（画面は 92.4）。

## 94. 版上げを 1 回で行う・update の出力を読みやすくする（2026-11-05 依頼者。導入先のレビュー指摘）
0.2.1 の適用で: 版上げに update・npm ci・check・データ検証・テスト・ビルドを 1 つずつ打った、update が自動でコミットしたことに気づきにくい、`update --dry-run` の出力が画面からあふれた、社内で足したテスト用のデータが使われないまま残っていた、サンプルのまま残ったデータを手で空にした、PowerShell で日本語が化けた、変更履歴の手順どおり先に `.gitlab-ci.local.yml` を作ると「コミットしていない変更」で止まった。作り変えはパッケージ側で行う（社内のスクリプトにしない。どの導入先でも同じ手順にするため）。
- **`yojitsu-navi upgrade [フォルダ]`**（`packages/app/lib/upgrade.mjs`）: ①`update` ②依存（`node scripts/ci/install.mjs`。CI の before_script と同じ）③`check` ④`npm run validate` ⑤テスト（`npm run typecheck`・`npm test`。既定は飛ばす。`--test` か環境変数 `YOJITSU_RUN_TESTS=1`。§79.2 の CI と同じ考え）⑥`npm run build` を順に行い、失敗した手順で止める（残りは「未実行」）。最後に手順ごとの結果（済み・失敗・飛ばした・未実行、件数・かかった秒）を出す。`update` のオプション（`--overwrite`・`--keep-local`・`--no-commit`・`--force`）を受け付ける。終了コードは `update` の社内の変更で止まれば 2、ほかの失敗は 1。
- **ログ**: `upgrade` は画面に要約だけを出し（`update` は `--summary` と同じ。npm の出力は出さず、失敗したときだけその手順の最後の 40 行を出す）、全部を `.yojitsu-navi-log/upgrade-<年月日-時分秒>.log` に書く（`--log <ファイル>` で変える）。`.yojitsu-navi-log/` は区分「コマンドのもの」で git に入れない（`.gitignore`。古い版の `.gitignore` でも `update` の `git status`・`git add` はこのフォルダを除く）。
- **`--log <ファイル>`**（`update`・`check`・`reset-data`）: 出力を UTF-8（BOM 付き。メモ帳・PowerShell 5.1 の `Get-Content` でも化けない）のファイルにも書く。止まったときのメッセージも書く。画面の文字コードは変えない（`chcp` はコンソール全体を変えてほかのプログラムに響くため）。PowerShell で化けるときの対処（`[Console]::OutputEncoding`）は `docs/DEPLOY_GITLAB.md`。
- **`--summary`**（`update`）: 画面には件数（変更・追加・削除・一覧の件数・変更履歴の行数）と、社内で変えたファイルの一覧（止まるかどうかの判断に要る）だけを出す。ファイルの一覧・差分・変更履歴の中身・新しい設定の項目は `--log` のファイルにだけ書く。
- **コミット**: 自動でコミットしたら「【自動でコミットしました】ブランチ <名前>（<元のブランチ> から作成）に「…」（<短いハッシュ>）」と取り消し方を出す。同じ名前のブランチがあれば `update-<版>-2` のように番号を付ける（前は今のブランチにコミットしていた）。`--no-commit` はブランチを作らずコミットもしない（`git add` まで。git の除外設定に当たるファイルも入れておく）で、MR にする手順を出す。

## 97. 作業名から案件名を抜き出して紐付ける（2026-11-05 依頼者。導入先のレビュー指摘）
「mapping.csv への作業コードの事前登録を必須にしたくない。作業名の目印より前が案件名なので、contracts.csv の案件名と一致すれば作業コードが未登録でも紐付けたい。目印の後ろの書式は判定に使わない。contracts.csv に無い案件名だけを未登録として警告したい。未登録の作業コードはエラーにせず、新しいコード・名前の変更・監査に使う。表記揺れは別名を明示的に登録したい。曖昧一致で勝手に割り当てない」への対応。依頼者は「完全一致ならやる」（2026-11-05）。

### 97.1 設定とデータ
- `config.json` の `projectFromTask`（省略可。無ければ使わない）: `marker`（運用保守の目印。空なら使わない）、`enabled`（`false` で止める。既定 `true`）。リポジトリの `config.json` は `enabled: false`（ダミーデータの作業名は目印より前が案件名ではないため）。
- `data/project-aliases.csv`（省略可）: `alias, project_name`。作業名から抜き出した名前 `alias` を contracts.csv の `project_name` として扱う。
- 目印の照合は `normalizeKeyword`（NFKC・小文字・空白を除く）と同じく全角半角・空白を区別しない。案件名は作業名（NFKC）の**最初の**目印より前を前後の空白を除いたもの。目印の後ろ（括弧内の表記など）は使わない。案件名の照合は §4.1 の `normalizeName` 後の完全一致。

### 97.2 紐付けの順序（§86.1 の 4. に足す）
1. mapping.csv の作業コードの行（§92）
2. mapping.csv の名前の行（(顧客, 案件) → (顧客, "")）
3. 作業名に目印があれば、抜き出した案件名が contracts.csv の `project_name` と完全一致する契約。無ければ別名で引いた `project_name` の契約。顧客名は見ない（空でもよい）。
4. どれも無い → 目印があれば未紐付け「未登録の案件」（`UNREGISTERED_PROJECT`）、無ければ従来どおり（顧客名が空なら除外、あれば `NO_RULE`）。
- 人が書いた mapping.csv の行が先（作業名と違う案件に入れたいときは mapping.csv に書く）。
- 3. の候補の契約から作業日の月が契約期間に入るものを選ぶのは §86.1 の 6. と同じ（契約の更新で同じ案件名の契約が 2 つあっても期間で分かれる。重なれば `MAPPING_AMBIGUOUS`）。0 件は `OUT_OF_PERIOD`、すべて不備で除外中なら `EXCLUDED_CONTRACT`。
- 未紐付けの一覧・警告は、抜き出した案件名ごとにまとめ、案件名の欄にその名前を出す。

### 97.3 運用保守かどうか（§86.1 の 2. に足す）
- 作業コードの行がある・名前の行のキーワードで決まる作業は従来どおり。
- それ以外で作業名に目印がある → 運用保守。
- 目印が無く、作業コードの行も名前の行も無い作業 → 運用保守以外（種別は分類表の運用保守以外の group、無ければ「その他」）。「キーワードに合致しない作業」（§62.3）には出さない（件数が多いため）。名前の行がある作業は従来どおり分類表で決める。

### 97.4 作業コードの扱い
- 案件の判定には使わない（mapping.csv に行がある場合を除く）。作業名の案件名で契約が見つかる作業は「未登録の作業コード」（§92.4）に数えない。`onUnregistered: "stop"` も、案件名で契約が見つからない作業の作業コードだけで止まる。
- 作業名の変更（§92.4）は従来どおり出す。
- 取り込み（`npm run fetch`）では、取り込む前に無かった作業コードを「新しい作業コード n 件」としてログに出す（止めない。`taskCodeCheck` が無くても出す。10 件まで、残りは件数）。
- 同じ契約IDの 2 行目以降（§2 で計算から外れる行）の案件名は照合に使わない。

### 97.5 検証（`npm run validate`）
- `ALIAS_EMPTY`（error）: `alias` か `project_name` が空。
- `ALIAS_DUPLICATE`（error）: 同じ別名が複数の案件名を指す。その別名は照合に使わない。
- `ALIAS_SHADOWED`（warning）: 別名が contracts.csv の案件名と同じ（案件名の一致が先なので使われない）。
- `ALIAS_UNKNOWN_PROJECT`（warning）: 指す案件名が contracts.csv に無い。
- 未登録の案件は従来の `UNMAPPED_WORKLOG`（warning、理由「未登録の案件」）。エラーにはしない。
